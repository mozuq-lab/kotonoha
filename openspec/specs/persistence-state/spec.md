# 永続化の状態（persistence-state）

> **これは実装済みの振る舞いの baseline 書き取りである**（是正計画 §5 条件2）。
> propose → apply の対象ではない。根拠は ADR-005 と Phase 3 WP-1 / WP-5 の実装。

## Purpose

端末内にしかデータが無い利用者にとって、「保存できたように見えて消える」は
起動しないことより重い。永続化が使えているかを型で表し、**保存できない状態を
利用者に伝えたうえで動作を継続する**（起動はブロックしない）。

## Requirements

### Requirement: 永続化の状態は3つで、box の利用可否から導かれる

システムは永続化の状態を `Ready` / `RecoverableFailure` / `Unavailable` の
3つで SHALL 表す。状態は領域（history / presetPhrases / favorites）ごとの
利用可否から機械的に導出されなければならない。

「復旧可能（Recoverable）」は**次回起動で直りうる**という意味である。非破損エラー
（ディスクフル・権限）では box を削除しないため、原因が解消すれば次回は開ける。

#### Scenario: すべての領域が利用できる
- **WHEN** history / presetPhrases / favorites のすべてが利用可能である
- **THEN** 状態は `Ready` になる

#### Scenario: 一部の領域だけ利用できない
- **WHEN** 一部の領域だけが利用できない
- **THEN** 状態は `RecoverableFailure` になる
- **AND** 利用できない領域の集合を保持する

#### Scenario: どの領域も利用できない
- **WHEN** すべての領域が利用できない
- **THEN** 状態は `Unavailable` になる

### Requirement: 保存できないことを利用者に伝える

システムは保存できない領域があるとき、その事実を**常設バナー**で利用者に
SHALL 伝える。バナーは `OfflineBanner` と同じ列に常に存在し、`Ready` のときだけ
高さ0で見えなくなる（表示・非表示で配置が動かないようにするため）。

#### Scenario: 保存できているときは何も出さない
- **WHEN** 状態が `Ready` である
- **THEN** バナーは高さ0で、文言を1つも表示しない

#### Scenario: すべて保存できないとき
- **WHEN** 状態が `Unavailable` である
- **THEN** 「保存できません。アプリを閉じると消えます」の主旨の文言を表示する

#### Scenario: 一部だけ保存できないとき
- **WHEN** 状態が `RecoverableFailure` で、保存できない領域が「定型文」である
- **THEN** 対象領域の名前を含む文言を表示する

### Requirement: 保存できなくても基本機能は使える

システムは永続化が利用できない場合でも、文字盤入力と TTS 読み上げを
SHALL 継続して提供する（NFR-301）。起動をブロックしてはならない。

#### Scenario: 永続化が全滅した状態で起動する
- **WHEN** すべての box が開けない状態でアプリを起動する
- **THEN** アプリは起動し、文字盤で入力して読み上げできる
- **AND** 保存できないことがバナーで示される

### Requirement: 「保存できているか」の真実は1つ

システムは「保存できているか」を**1つの出所**から SHALL 導かなければならない。
状態の判定と、実際に保存を行う経路（repository）が別々に同じ述語を評価しては
ならない（ADR-005「1概念1真実」）。両者が独立に評価されると、評価時点の違いで
「バナーは出ないのに保存されていない」が起きうる。

#### Scenario: repository が使えない領域は保存できない領域として扱われる
- **WHEN** ある領域の repository が利用できない
- **THEN** その領域は保存できない領域として状態に反映される

### Requirement: box が開いていても、書き込みの失敗は保存できない状態に合流する

システムは、box が開いていても書き込みが失敗した領域を「保存できない領域」として
SHALL 扱う。hive は書き込み失敗で box を閉じないため、box の開閉だけでは
ディスクフル・権限・Web の quota による失敗を観測できない。

記録は自己回復しなければならない——一度の失敗で恒久的に警告を出し続けると、
原因が解消しても利用者には分からない。

#### Scenario: 書き込みが失敗した領域が保存できない領域になる
- **WHEN** box は開いているが、ある領域への書き込みが失敗した
- **THEN** その領域は保存できない領域として扱われ、バナーに反映される

#### Scenario: 次の書き込みが成功したら警告が消える
- **WHEN** 失敗を記録した領域で、次の書き込みが成功する
- **THEN** その領域は保存できない領域から外れる

### Requirement: 永続化面の変更は検査を通る

システムは、永続化される型（`typeId`）・永続フィールドの並びと型・開く box が
無断で変わっていないことを CI で SHALL 検査する（ADR-005 の検査条項、
ADR-007 リリース条件1d）。

検査は**権威の出力を消費**しなければならない。`lib/` のソースを文字列照合する
検出器を作ってはならない（ADR-008 の教訓1）。検査が見る登録経路は、
**本番が実際に使う登録経路そのもの**でなければならない。

#### Scenario: 永続化する型が増えたら落ちる
- **WHEN** 本番の登録経路に新しい `TypeAdapter` が追加される
- **THEN** 許可リスト検査が失敗する

#### Scenario: 永続フィールドの並びや型が変わったら落ちる
- **WHEN** ある `TypeAdapter` の永続フィールドの番号を詰め直す、型を変える、
  またはフィールドを増減させる
- **THEN** 許可リスト検査が失敗する

#### Scenario: box が増えたら落ちる
- **WHEN** 永続化の領域（box）が追加される
- **THEN** 許可リスト検査が失敗する

### Requirement: 破損した box は退避してから作り直す

システムは破損した box を検出したとき、削除の前に退避を SHALL 行う。
退避に失敗した場合はデータ保全を優先して削除を中止しなければならない。
破損と断定できない失敗（ディスクフル・権限等）では box を削除してはならない。

#### Scenario: 破損していない失敗では box を消さない
- **WHEN** box のオープンが、破損を示さないエラーで失敗する
- **THEN** box ファイルは削除されず、その領域は利用不可として扱われる

#### Scenario: 退避できないときは削除しない
- **WHEN** box が破損しているが、退避に失敗する
- **THEN** box ファイルは削除されず、その領域は利用不可として扱われる
