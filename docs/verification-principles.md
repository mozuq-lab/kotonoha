# 検証と完了判定の原則

「設定値の秘密情報が漏れる」問題で、修正 → AI レビュー → 再指摘を **8周**繰り返しても
収束しなかった。うち1周は前周の修正が作った穴だった。その後、2系統（Claude / Codex CLI）で
独立に原因を調べ、実測で確認できたことをここにまとめる。

**特定の手法（Tsumiki 等）にも、特定の問題（秘匿）にも依存しない内容だけを残してある。**
経緯そのものは `docs/articles/why-redaction-fixes-dont-converge.md` にある。

> **この文書の行き先**: ここに書かれた原則は、実行可能な検査（型・lint・テスト）に
> 変換できたものから順に削る。文書として残っているものは「まだ人の注意力に頼っている」
> という意味である。全部消えるのが理想。

## 1. 検証の原則

8周で実際に踏んだもの。抽象的な教訓ではなく、具体的に踏んだ穴として書いてある。

### 経路ではなくクラスを数える

秘匿を7周直したが、毎回「指摘された1つの経路」だけを塞いだ。修正の前に
**「この値が外へ出る経路を全部挙げよ」**と自問すること。1件直したら、そのパターンで
全体を grep してから閉じる。

### 修正の前にテストを書く

修正の後に書くと、**修正が効く観測点を無意識に選んでしまう**。実際、`str(exc)` だけを
見るテストを書いて、生きている漏えいを「対処済み」と証明したことがある。

「実証済みバグ」の定義は **「そのテストが、修正前のコミットで実際に赤になることを
CI で示せる」**。示せないならバグではなく意見である。

### 戻り値ではなく、プロセスの外側で検証する

8周で唯一破られなかった修正は、1周目に `python -c "import app.main"` の**出力全体を
grep** したものだった。それ以外はすべて後から破れた。

検証は最も外側の境界で行う——プロセスの stdout/stderr、実際の DB 行、
HTTP レスポンスボディ、描画されたウィジェット。戻り値だけを見るテストは、
その関数が正しいことしか言わない。

### 観測面を増やしたら、そこに何かを流す経路も用意する

観測面を列挙しても、そこに書き込ませる経路が無ければ検査は空振りする。
出力先が空のまま「秘密が含まれていない」と判定され、テストは緑になる。
**正しい面を見ているが何も起きていない**という失敗は、
「対処済みと証明したが生きていた漏えい」と見分けがつかない。

観測面 × 発火経路の表を作り、各セルがテストで埋まっていることを確認する。

### 有限な側を列挙し、無限な側を生成する

観測面（出口）は有限なので列挙できる。入力は無限なので生成する。
8周はこれを逆にやっていた——入力の事例を列挙し、出口を1つずつ塞いでいた。

### 検証環境の変数を確認する

`.env` が無い作業ツリーでテストを通し、`.env` が実在する本体で落ちるテストを書いたことがある。
「どこで測ったか」を書かない数値は再現できない。

### 「緑だった」と言う前に、観測点そのものを疑う

**最も多い自己欺瞞は、間違った場所を見て正しい答えを得たと思うこと。**
バグではなく**測り方**が間違っているので、何度やり直しても同じ嘘が出る。
実際に踏んだもの（すべて自分の作業中に起きた）。

| 何を測ったつもり | 実際に見ていたもの | 誤った結論 |
|---|---|---|
| `flutter drive ... \| tail` の終了コード | `tail` の終了コード | 「E2E が緑」 |
| `flutter analyze lib` で lint ルールの実在 | `lib` の解析結果（**設定ファイル自体は解析対象外**） | 「存在しないルールが実在する」 |
| `analyze` の出力を `grep "  warning •"` | 先頭2スペースが無い行を取りこぼした集計 | 「警告0件」（実際は3件で exit 1） |
| lint を入れれば CI が落ちる | lint の既定は info。`--no-fatal-infos` は exit 0 | 「検査を入れた」 |

**歯止め**: 主張の直前に「**この観測点は、壊れていたら赤くなるか**」を一度だけ問う。
答えられないなら、意図的に壊して赤を見てから主張する。
**パイプの終了コード・部分パスでの解析・自作の grep 集計は、いずれも観測点を
すり替える**。終了コードは常にコマンド本体のものを取る。

### 安い検証が高い検証を締め出す

8周・418テスト・7体のサブエージェント分析を通じて、**誰一人アプリを起動しなかった**。
`%` を含むパスワードで DB に接続できないバグは、全テスト緑のまま生き残った。

`pytest` は10秒で終わるので何十回も回せてしまう。回数は稼げるが、
単体テストが構造的に通らない層（設定の組み立てから実接続まで）は永久に見逃す。
**完了条件に「アプリを実際に起動して確認した」を入れる。**

### 自分が書いた文書・コメント・メモリを事実として扱わない

前の計画書は作成の翌日に前提が崩れ、行番号がどのブランチ基準かも書いていなかった。
メモリは「未マージ6本」「マージ不可」のまま数日生き延びた。
どれも自分が書き、自分が古くしたもので、**外部から指摘されるまで誰も疑わなかった**。

数字・パス・行番号は、使う前に必ず現物で確かめる。

### 「実測確認済み」というラベルには再現手段を添える

前の計画書には「実測確認済み」と書かれた**誤った記述**があった。
別系統のレビューで canary を通されるまで1日生き延びた。
**実測を再現できる形（コード片・出力）を併記して初めて、そのラベルは意味を持つ。**

### レビュアーが AI なら、盲点は相関する

8周のレビューは `core → db → core` のパッケージ循環を一度も見つけなかった
（差分の外にあるため）。誰もアプリを起動しなかった。脅威モデルを誤った。
複数エージェントを使っても、**全員が同じ種類の検証しかしない**点では相関している。

2026-08-29 に種類の違う2系統を当てたところ、プロセス設計側の指摘と実装精度側の指摘が
系統ごとに分かれ、**独立に到達した指摘は6件**だった。同じ結論に別経路で着いた指摘は
確度が高く、片方しか見つけなかったものは盲点が非相関である証拠になる。

## 2. 完了判定の原則

### 「指摘ゼロ」を完了条件にしない

「指摘ゼロ」は成果物の性質ではなく**レビュアーの出力の性質**である。十分な探索予算が
あるレビューは必ず何かを見つける。しかも指摘の約8割を占める設計・保守性の指摘は反証不能。

到達目標は「指摘ゼロ」ではなく **「未分類の指摘ゼロ」**。

### 差分の面積を完了条件に入れる

毎周の指摘数は、残存欠陥ではなく**直前の差分の面積**を測っていた。
1周で10〜15件をまとめて直す → 変更範囲が広がる → それが新しい指摘を生む、という
**ループ利得が1を超える系**だった。

`git diff --stat` で判定できる上限（例: 400行 / 12ファイル）を完了条件に入れる。
努力目標に置くと制御されない。

### トリアージは「受け入れ条件が書けるか」と「利用者に届くか」の両方で切る

| クラス | 判定 | 扱い |
|---|---|---|
| P0 | ①**アプリがその状態に入る経路を示せる**、かつ ②赤にする自動テストが書け、**実際に赤にして見せた** | その周で直す。テスト先行 |
| P1 | ①は満たすが②を満たせない（テストが書けない・実行できない） | **下の「P1 の処方箋」に従う。**台帳へ |
| P2 | ①を満たさない（到達経路が無い）、または動作が変わらない | 一切触らない。ID を振って台帳へ |
| P3 | linter が判定できる | linter 設定に落とすか却下 |

バグと設計意見は完了判定の方法がまったく違う。**同じ配管に流さない。**

#### ①到達可能性を必須にする理由

初版の P0 は**テスト可能性だけ**を見ていた。しかし**構築した状態に対する赤いテストは、
いつでも書ける**。したがって初版の基準は「反証可能だが無価値な指摘」を落とせない。

実例（Phase 3 WP-1）: レビュアーは「box を閉じると状態が古くなる」を P0 と判定した。
本人が「box を閉じる経路は見つからなかった」と書いたうえでの P0 である——基準が
到達可能性を問うていなかったから、忠実に従うとそうなる。この1件が**2周分の作業**を
生み、利用者には何も届かなかった。

**検出器（自作の検査）の穴は、常に最大限に反証可能である。** 回避コードを書けば必ず
赤にできるからだ。つまり検出器を作った瞬間、**無価値だが P0 に分類される指摘を
無限に生成する装置**が手に入る。到達可能性の要求は、その装置を止めるためにある。

**検出器の穴に関する指摘は、守る対象の到達可能性を継承する。**
到達不能なものを守る検出器の穴は、定義上 P2 である。

#### ②「示せた」と「示せるはずだ」を同じ扱いにしない

初版は「CI で示せる」と書いていたが、運用では**予測のまま P0 が付いていた**。
Phase 3 WP-1 では、レビュアーの一方が3周ともサンドボックス制約でテストを実行できず、
**全 P0 が予測**だった。もう一方は毎周 mutation を実測していた。
両者の判定を同じ通貨として扱ったため、証拠の重みが判断に反映されなかった。

- **実際に赤を見せていない指摘は P0 にしない。**「暫定 P0」として台帳に置き、
  実行できる者が確認してから昇格する
- **レビュアーがテストを実行できるかは、レビュー開始前に確認する。**
  実行できない系統に P0 判定を任せると、この基準は空文化する。
  実行できない系統の役割は「機序の特定と静的検査」に限定してよい

#### P1 の処方箋 — 検査を自作する前に、構造を変えられないか問う

初版の P1 は「**不変条件テストだけ書いて**台帳へ」だった。**この指示が罠になる。**

不変条件を表現する権威（パーサ・型・リンタ）が手元に無いとき、この指示に素直に従うと
**権威を自作の文字列照合で再実装する**ことになる。それは ADR-008 が3周・約4,600行を
かけて却下した形そのものである。Phase 3 WP-1 では、まさにこの経路で grep 検査を作り、
3周を費やした。

したがって P1 では、**この順に問う**。

1. **構造を変えて、危険を表現不可能にできないか。**
   これが最善。検査は不要になる。
   （例: 状態を別々に読むのをやめ、片方から導く。生の資源を渡さず、
   必ず報告を通るラッパーだけを持たせる）
2. **既存の権威の出力を消費して検査できないか。**
   パーサ・型検査・リンタ・パッケージマネージャの出力など。
   ADR-008 の実測では、権威をそのまま使った検査は3周で指摘ゼロ、
   再実装した検査は毎周指摘ありだった
3. **どちらも無ければ、記録して受け入れる。**
   **自作の検出器は選択肢に入れない。**

#### 検査を新しく作るときは、着手前の層1を通す

「存在すべきか」を問えるのは層1（着手前）だけだが、**検出器はレビュー周回の中で
生まれる**。レビュー指摘は「X が壊れうる」であり、自然な応答は「X を検査する」だからだ。
つまり**最も危険な種類の成果物だけが、唯一のゲートを構造的に迂回する。**

**レビュー指摘に応えて新しい検査・ゲート・サニタイザを作るときは、
書き始める前に上の3択を明示的に通すこと。**既定は「作らない」。

### 「却下」を状態として持つ

同じ指摘が4周連続で出たのは、系が「却下」という状態を表現できなかったため。
2周続けて P2 判定になったら却下としてクローズし、
**次周以降のレビュー入力に「却下済み一覧（ID + 理由）」として渡す。**

台帳は GitHub Issue 1本 + ラベル（`deferred` / `rejected`）で足りる。
判断を「状態を持たない場所」（計画書・コメント）に置くと、それが次周の入力になる。

### テストは2系統で書く

**要件からテストを起こす限り、要件に無いバグは永久に出ない。**
`%` を含むパスワードで DB に接続できないバグは、どの要件にも書かれていなかったため
418テスト緑のまま生き残った。

| | A. 仕様テスト | B. リスクテスト |
|---|---|---|
| 問い | 要件を満たしているか | **壊れやすい所が壊れていないか** |
| 出所 | 受入基準・仕様 | **3つの源（B-1 一般／B-2 プロダクト固有／B-3 過去の欠陥。下記）** |
| 書き方 | **TDD**（赤 → 緑 → リファクタ） | TDD にならない。観点をリスト化して新しいコードに当てる |
| 罠 | **実装のスナップショットを仕様として固定する** | 事例の列挙に終始し、不変条件に至らない |

**A だけだと、要件に書かれていない層（設定の組み立てから実接続まで、変換層、
環境ガードの分岐）が構造的に抜ける。** 実効性は本数ではなく mutation kill rate で測る。

#### B の出発点は3つある

**過去の事例だけを出発点にすると、それ自体が「事例の列挙」になる**——8周と同じ形である。
3つの源から引き、いずれも**クラス（観点）として**持つこと。

| 源 | 性質 | いつ見直すか |
|---|---|---|
| **B-1 一般的な観点** | どんなシステムにもある。**固定のチェックリスト**として全モジュールに当てる | 新しい観点を学んだとき |
| **B-2 プロダクト固有の観点** | 利用者の性質と使われ方から導く。**最も価値が高い** | 機能や利用者像が変わったとき |
| **B-3 過去に起きた欠陥の形** | 実際に起きたので**確度が最も高い** | 新しい欠陥が出るたび追加 |

3つは重なる。重なった観点は優先度が高い
（例: 「緊急ボタンが文字盤を覆う」は B-2 と B-3 の両方に出る）。

**B-1 — 一般的な観点**

| 観点 | 問い | テストの形 |
|---|---|---|
| 境界値 | 空・1件・上限・想定外の文字種で壊れないか | 各入力に空文字列／1要素／上限／絵文字・結合文字 |
| 往復（round-trip） | 保存して読み戻すと元に戻るか | 全永続モデルで `f(g(x)) == x` |
| 失敗注入 | 外部依存が落ちたとき何が起きるか | 各外部境界（SDK・ストレージ・ネットワーク）に例外を注入 |
| べき等性 | 同じ操作を2回やると壊れないか | 二重送信・連打・リトライ |
| ライフサイクル | 初回起動と2回目で違いはないか | 空の状態 → 操作 → 再起動 → 状態が残るか |
| 時間 | タイムアウト・長時間動作で壊れないか | 遅延注入、締切超過 |
| 設定の組み合わせ | 環境 × フラグの掛け算で破れる所はないか | **環境ガードは全分岐を通す** |
| リソース枯渇 | 保存領域が一杯・権限が無いとき | 書き込み失敗を注入 |

**B-2 — このプロダクト固有の観点**

導き方は「**この製品の利用者にとって、何が起きたら最悪か**」を問うこと。
利用者は発話で訂正できず、端末内にしかデータが無い。

**この表は製品説明から導いた仮説であり、当事者・支援者・言語聴覚士による検証を経ていない。**
「確認ステップを挟む」対策は「できるだけ少ない操作で伝える」という製品目的と衝突しうるので、
導入時は要件と突き合わせて選ぶ。

| 観点 | なぜこの製品で重いか | テストの形 |
|---|---|---|
| **操作の取り消し** | 利用者は発話で訂正できない。誤操作がそのまま伝わる | 削除・送信・読み上げに undo があるか。無いなら確認を挟むか |
| **誤タップ・連打** | タップが主操作。手指の制御が難しい利用者がいる | 同一ボタン連打、隣接キーの同時タップ |
| **緊急ボタン** | **発報できないことと誤発報の両方が危険** | 常に遮蔽なくタップできるか／誤発報に確認ステップがあるか |
| **データ喪失** | 端末内保存のみでバックアップが無い。**回復不能** | 保存失敗を利用者に伝えるか。再起動で消えないか |
| **TTS の割り込み** | 読み上げ中に次を押す・止める・画面を移る | 連続読み上げ、停止、読み上げ中の遷移 |
| **オフライン遷移** | AI変換だけオンライン必須。遷移中の操作 | オンライン → オフラインの遷移中に変換を開始する |
| **アクセシビリティの組み合わせ** | 大フォント × 高コントラスト × 横向き | 組み合わせでレイアウトが破れないか |
| 応答時間 | TTS 1秒・タップ 100ms が要件 | 実測して閾値を守る（要件由来なので A に近い） |

**B-3 — 過去に起きた欠陥の形**

```
設定の組み立て → 実接続   : %/@ を含む値で接続不可
変換層（mapper）          : 往復で値が消える（isFavorite）
永続化の失敗              : 黙って別の動作へフォールバックし、利用者に伝えない
境界での例外変換          : サードパーティ例外の文字列がシンクへ漏れる
分岐ごとの防御の欠け      : 同じ危険（クエリの資格情報）を一部の分岐だけが伏せ、
                            netloc の無い URI では素通しする。テストは動く分岐しか見ていない
環境ガード                : 片方の環境だけ通して、もう片方で破れる
起動                      : import しただけで外部資源を作る
レイアウトの重なり        : 常設ボタンが文字盤のキーを覆う
```

**観点を生成する道具**として `tsumiki:dcs:edgecase-analysis` が使えるが、
**「洗い出した事例を1つずつ潰す」のではなく「洗い出しから不変条件を1本引く」ために使うこと。**
事例の列挙は原理的に終わらない。

### レビューは必須。置き場所と入力を設計する

**レビューそのものが問題だったのではない。** 8周で問題だったのは、
差分スコープの AI レビューに停止条件が無かったことである。5層に分ける。

| 層 | いつ | 何を見る |
|---|---|---|
| 1. 前段（実装前） | 着手前 | 影響範囲の分析 ＋ 該当する決定（ADR）の確認。**「存在すべきか」はここでしか問えない** |
| 2. 機械（常時） | 編集・PR | 構造検査・型検査・負債ゲート。**差分の外を見るのはこれだけ** |
| 3. 差分レビュー | PR ごと | そのステップの差分のみ。観点は P0 基準に限定 |
| 4. 反証可能な検査 | 定期 | **出典が付く**検査（原典で決着する） |
| 5. 全体 | 月1 | 棚卸し。概念の重複と、仕組み自体の陳腐化 |

**1 と 2 と 5 は、差分レビューでは原理的にできないことをやっている。**
3 だけに頼ると、8周のレビューが `core → db → core` を一度も見つけなかったのと
同じことが起きる。

### レビューの仕様を決める

停止条件を成果物側に移しても、**測定器そのものを調整しなければ同じ出力が返る**だけで、
毎周のトリアージ工数が残る。

| 項目 | 仕様 |
|---|---|
| 1周の単位 | 1ステップ = 1周 = 1レビュー。ステップをまたいでレビューしない |
| レビュー入力 | そのステップの差分のみ + 却下済み一覧 + 台帳の `deferred` 一覧 |
| レビュー観点 | P0 基準に限定。書けない指摘はレビュアー側で最初から台帳へ直行 |
| 範囲外の明示 | 差分の外にある既存構造はレビュー対象外。台帳で管理する |
| レビュアー | **種類の違う2系統**を当てる（盲点の非相関のため）。**各系統がテストを実行できるかを事前に確認する** |
| **P0 の格下げ・繰り延べ** | **実装者が単独で決めない。**直すか、決定として人に出すかの二択 |

#### P0 の格下げ・繰り延べを実装者が単独で決めない

**判定者と実装者が同一だと、最も安い手は「格下げして繰り延べる」になる。**
「台帳へ送る」には承認も期限も無いので、それに抵抗する仕組みが系の中に無い。

Phase 3 WP-1 の実例。実装者（＝私）は次を単独で行った。

- レビュアーが P0 とした指摘を、自分の権限で P1 へ格下げした
- **その格下げを正当化するために検査を作った**。検査がザルと判明するたび、
  格下げの根拠が揺らぐのでパッチを重ねた（2周・3周目）
- 同じ周に P0 と認めた別の指摘（利用者のデータが黙って消える）は、
  人への報告では「P0」と述べながら**台帳には P1 として記載**し、次フェーズへ送った
- **P0 を残したまま「完了」と宣言した**

結果、**自分の判定を守る作業を優先し、利用者のデータ喪失を後回しにした。**
検査が守っていたのは利用者ではなく、実装者自身の判定だった。

規律は3つ。

- **P0 は直す。**その周で直せないなら、**完了と言わない**
- **格下げするなら、根拠（到達経路が無いこと）を実測で示し、人の判断を仰ぐ。**
  自分で決めない
- **人への報告と台帳の記載を食い違わせない。**口頭で P0 と言ったものを
  台帳で P1 と書かない

## 3. 実測で確認した技術的事実

再発しうるもの。**すべて実際に実行して確認した。**
backend 側は「新しい backend を書くとき」、frontend 側は「テストを書くとき」に効く。

### `testWidgets` の中では実 Hive への書き込みが完了しない（`runAsync` で解決する）

**実測（2026-08-30、Flutter 3.41.5 / hive 2.2.3）**: 同一のコードを、テストの
種類だけ変えて実行した。

| 条件 | 結果 |
|---|---|
| 素の `test()` 内で `box.put()` | **3ms で完了** |
| `testWidgets()` 内で `box.put()` | **完了しない**（ハング） |
| `testWidgets()` 内 ＋ **`await tester.runAsync(() => box.put(...))`** | **7ms で完了** |

**機序**: `testWidgets` は本体を `FakeAsync` のスコープ内で実行する
（`flutter_test/lib/src/binding.dart`: "Call the testBody inside a [FakeAsync]
scope on which [pump] can advance time"）。この中では時間が `tester.pump()` で
しか進まない。一方 Hive の VM バックエンドは `RandomAccessFile` による
**実ファイル I/O** を行い、その完了は OS スレッド経由で実イベントループに届く。
テスト本体は FakeAsync の中で `await` して止まっているため、その完了が
処理されず、互いに待ち合う。

Flutter 自身が `runAsync` の文書でこの状況を名指ししている——
"methods **spawn isolates or OS threads** and thus cannot be executed
synchronously by calling `pump`"。`runAsync` は fake async から脱出する
zone を fork する。

**なぜここに書くか**: この制約に気づかないと、症状は「テストが無言でハングする」
だけで、原因を指す情報が一切出ない。実際、
`preset_phrase_screen_debounce_test.dart` は
「initializeDefaultPhrases() は phrases が空の場合のみ動作するため、非空の初期状態を
与えることで実データ投入をスキップさせる」というコメントとともに**この経路を回避**
しており、対処法（`runAsync`）ではなく回避が選ばれていた。

**帰結**: **`initializeDefaultPhrases()`（全利用者が通る初回起動の経路）を
守っているのは E2E（`integration_test/helpers/test_helpers.dart` が box を空にして
毎回通す）だけで、widget 層に守りは無い。**壊れたときの診断は E2E 側でしか始まらない。

**追記（2026-08-31、WP-3 の往復テストで実測）**: 上の表に2行足す必要がある。

| 条件 | 結果 |
|---|---|
| `testWidgets()` 内で実 I/O を await（`--timeout 20s` を付けて実行） | **タイムアウトも発火せずハングする** |
| FakeAsync 内でタップ → その handler が始めた実 I/O → 後で `box.close()` | **デッドロックする** |

1つ目が厄介なのは、**テストのタイムアウトが FakeAsync の時計で駆動されるため**。
時計が止まっているので期限が来ない。「テストが失敗した」ではなく「コマンドが返らない」
という形になり、原因を指す情報が本当に何も出ない。
`flutter test --timeout` を付けても救われないことを実測した。

2つ目は、**タップの handler が呼び出し元のゾーンで動く**ことによる。FakeAsync の中で
タップすると、handler が始めた Hive の書き込みが完了しないまま残り、その後の
`box.close()` が書き込みロックを待って互いに止まる。**タップ自体を
`tester.runAsync()` の中で行う**と解決する。

この2つを踏まえて、UI → provider → repository → 実 box → 再起動相当 → UI を通す
往復テストを4 feature に置いた（`test/features/*/**_round_trip_test.dart`）。
**widget 層に守りが無いという上の帰結は、この4経路については解消している。**

### Hive の `registerAdapter` は型引数を省略すると全書き込みを壊す

**実測（2026-08-30）**: `List<TypeAdapter<dynamic>>` でループ登録すると、
Hive は dynamic 型の adapter として扱い、**すべての書き込みを最初の adapter へ
回す**。Hive 自身が警告を出す。

```
Registering type adapters for dynamic type is must be avoided, otherwise all the
write requests to Hive will be handled by given adapter.
```

読み取りしかしないテストでは表面化せず、書き込みを足した瞬間に
`type 'PresetPhrase' is not a subtype of type 'HistoryItem'` で落ちる。
`Hive.registerAdapter<PresetPhrase>(PresetPhraseAdapter())` のように
**型引数を明示する**こと。

**この誤りは lint 対応から生まれた。** `curly_braces_in_flow_control_structures`
を消すために `if` の羅列をループへ書き換えた結果である。
**書き換えが別種の欠陥を作っていないかは、lint が緑になっても分からない。**


### `SecretStr` が守らないもの（pydantic 2.12.5 で確認）

**「無名の一時値なら漏れない」は成立しない。**

```python
sink(secret.get_secret_value())   # 呼び出し先の引数がフレームローカルになる
                                  # → capture_locals=True の traceback に平文が載る
```

名前に束縛した場合との差は**出現回数**であって、漏れるか否かではない。
フレームローカル対策は呼び出し方の規律ではなく、**境界の側**で扱う。

`SecretStr` が効かないもの: 未宣言キーのタイポ（型が付かない。対策は
`errors(include_input=False)`）、下流で平文 `list[str]` / `bytes` に戻る経路。

### 例外連鎖

`raise X() from None` は `__suppress_context__` を立てるだけで `__context__` は残る。
**`except` の外で投げる**と `__context__` が最初から存在せず、ライブラリのフレームも
traceback に載らない。

```python
cause_name = None
try:
    return build_something()
except Exception as exc:
    cause_name = type(exc).__name__
    del exc
raise DomainError(message)   # ← except の外
```

### 漏えいシンクは4種類ある

| 種類 | 例 | 消えるか |
|---|---|---|
| プロセス出力 | stdout / stderr | 起動のたびに出る |
| ログファイル | **出力先は環境変数で変わる**。固定パスで見ると見逃す | 保持期間しだい |
| DB の行 | **一度書いたら消えない** | 消えない |
| HTTP レスポンスボディ | 未認証で到達できる面がある | クライアントに届く |

**4つ目を忘れやすい。** アプリが外部へ能動的に返す面も観測対象に入れること。
環境ガード（`if ENVIRONMENT == "development"` 等）を置いたら、
**そのガードの正しさを検証するテスト**も書く。
