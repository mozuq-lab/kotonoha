# 検証と完了判定の原則

「設定値の秘密情報が漏れる」問題で、修正 → AI レビュー → 再指摘を **8周**繰り返しても
収束しなかった。うち1周は前周の修正が作った穴だった。その後、2系統（Claude / Codex CLI）で
独立に原因を調べ、実測で確認できたことをここにまとめる。

**特定の手法（Tsumiki 等）にも、特定の問題（秘匿）にも依存しない内容だけを残してある。**
経緯そのものは `docs/articles/why-redaction-fixes-dont-converge.md` にある。

> **この文書の行き先**: ここに書かれた原則は、実行可能な検査（型・lint・テスト）に
> 変換できたものから順に削る。文書として残っているものは「まだ人の注意力に頼っている」
> という意味である。全部消えるのが理想。

---

## 1. 検証の原則

8周で実際に踏んだもの。抽象的な教訓ではなく、具体的に踏んだ穴として書いてある。

### 経路ではなくクラスを数える

秘匿を7周直したが、毎回「指摘された1つの経路」だけを塞いだ。修正の前に
**「この値が外へ出る経路を全部挙げよ」**と自問すること。1件直したら、そのパターンで
全体を grep してから閉じる。

### 修正の前にテストを書く

修正の後に書くと、**修正が効く観測点を無意識に選んでしまう**。実際、`str(exc)` だけを
見るテストを書いて、生きている漏えいを「対処済み」と証明したことがある。

「実証済みバグ」の定義は **「そのテストが、修正前のコミットで実際に赤になることを
CI で示せる」**。示せないならバグではなく意見である。

### 戻り値ではなく、プロセスの外側で検証する

8周で唯一破られなかった修正は、1周目に `python -c "import app.main"` の**出力全体を
grep** したものだった。それ以外はすべて後から破れた。

検証は最も外側の境界で行う——プロセスの stdout/stderr、実際の DB 行、
HTTP レスポンスボディ、描画されたウィジェット。戻り値だけを見るテストは、
その関数が正しいことしか言わない。

### 観測面を増やしたら、そこに何かを流す経路も用意する

観測面を列挙しても、そこに書き込ませる経路が無ければ検査は空振りする。
出力先が空のまま「秘密が含まれていない」と判定され、テストは緑になる。
**正しい面を見ているが何も起きていない**という失敗は、
「対処済みと証明したが生きていた漏えい」と見分けがつかない。

観測面 × 発火経路の表を作り、各セルがテストで埋まっていることを確認する。

### 有限な側を列挙し、無限な側を生成する

観測面（出口）は有限なので列挙できる。入力は無限なので生成する。
8周はこれを逆にやっていた——入力の事例を列挙し、出口を1つずつ塞いでいた。

### 許可集合は、書き下して有限であることを確認する

「安全なトークンだけで組み立てる」と言いながら、無限集合を安全側に入れてしまう。
ホスト名を「厳格な文法に一致すれば安全」と分類した時点で、それは引き算に戻っている
（秘密が DNS 名として合法な文字列なら、そのまま出力される）。

**ライブラリが持つ集合を参照しておきながら手書きで足さない。**
`SCHEMES` を参照しつつ `| {"unix"}` を足し戻し、ライブラリに存在しないスキームを
信頼したことがある。しかも**そのテストが、存在しないスキームを正解として固定していた**。

### 正しい境界で検証する

`urllib.parse.urlparse` / `urlsplit` は percent-decode しないので、DSN の往復一致の
確認には使えない。`sqlalchemy.engine.make_url` を使うこと。
（この失敗は本番コードで直したあと、テストハーネス側に同じ形で残っていた。）

### 検証環境の変数を確認する

`.env` が無い作業ツリーでテストを通し、`.env` が実在する本体で落ちるテストを書いたことがある。
「どこで測ったか」を書かない数値は再現できない。

### 安い検証が高い検証を締め出す

8周・418テスト・7体のサブエージェント分析を通じて、**誰一人アプリを起動しなかった**。
`%` を含むパスワードで DB に接続できないバグは、全テスト緑のまま生き残った。

`pytest` は10秒で終わるので何十回も回せてしまう。回数は稼げるが、
単体テストが構造的に通らない層（設定の組み立てから実接続まで）は永久に見逃す。
**完了条件に「アプリを実際に起動して確認した」を入れる。**

### 自分が書いた文書・コメント・メモリを事実として扱わない

前の計画書は作成の翌日に前提が崩れ、行番号がどのブランチ基準かも書いていなかった。
メモリは「未マージ6本」「マージ不可」のまま数日生き延びた。
どれも自分が書き、自分が古くしたもので、**外部から指摘されるまで誰も疑わなかった**。

数字・パス・行番号は、使う前に必ず現物で確かめる。

### 「実測確認済み」というラベルには再現手段を添える

前の計画書には「実測確認済み」と書かれた**誤った記述**があった。
別系統のレビューで canary を通されるまで1日生き延びた。
**実測を再現できる形（コード片・出力）を併記して初めて、そのラベルは意味を持つ。**

### レビュアーが AI なら、盲点は相関する

8周のレビューは `core → db → core` のパッケージ循環を一度も見つけなかった
（差分の外にあるため）。誰もアプリを起動しなかった。脅威モデルを誤った。
複数エージェントを使っても、**全員が同じ種類の検証しかしない**点では相関している。

2026-08-29 に種類の違う2系統を当てたところ、プロセス設計側の指摘と実装精度側の指摘が
系統ごとに分かれ、**独立に到達した指摘は6件**だった。同じ結論に別経路で着いた指摘は
確度が高く、片方しか見つけなかったものは盲点が非相関である証拠になる。

## 2. 完了判定の原則

### 「指摘ゼロ」を完了条件にしない

「指摘ゼロ」は成果物の性質ではなく**レビュアーの出力の性質**である。十分な探索予算が
あるレビューは必ず何かを見つける。しかも指摘の約8割を占める設計・保守性の指摘は反証不能。

到達目標は「指摘ゼロ」ではなく **「未分類の指摘ゼロ」**。

### 差分の面積を完了条件に入れる

毎周の指摘数は、残存欠陥ではなく**直前の差分の面積**を測っていた。
1周で10〜15件をまとめて直す → 変更範囲が広がる → それが新しい指摘を生む、という
**ループ利得が1を超える系**だった。

`git diff --stat` で判定できる上限（例: 400行 / 12ファイル）を完了条件に入れる。
努力目標に置くと制御されない。

### トリアージは重要度ではなく「受け入れ条件が書けるか」で切る

| クラス | 判定 | 扱い |
|---|---|---|
| P0 | 赤にする自動テストが書け、修正前コミットで赤になることを CI で示せる | その周で直す。テスト先行 |
| P1 | テストは書けないが不変条件の形に言い換えられる | 不変条件テストだけ書いて台帳へ |
| P2 | 上2つが No、動作が変わらない | 一切触らない。ID を振って台帳へ |
| P3 | linter が判定できる | linter 設定に落とすか却下 |

バグと設計意見は完了判定の方法がまったく違う。**同じ配管に流さない。**

### 「却下」を状態として持つ

同じ指摘が4周連続で出たのは、系が「却下」という状態を表現できなかったため。
2周続けて P2 判定になったら却下としてクローズし、
**次周以降のレビュー入力に「却下済み一覧（ID + 理由）」として渡す。**

台帳は GitHub Issue 1本 + ラベル（`deferred` / `rejected`）で足りる。
判断を「状態を持たない場所」（計画書・コメント）に置くと、それが次周の入力になる。

### レビューの仕様を決める

停止条件を成果物側に移しても、**測定器そのものを調整しなければ同じ出力が返る**だけで、
毎周のトリアージ工数が残る。

| 項目 | 仕様 |
|---|---|
| 1周の単位 | 1ステップ = 1周 = 1レビュー。ステップをまたいでレビューしない |
| レビュー入力 | そのステップの差分のみ + 却下済み一覧 + 台帳の `deferred` 一覧 |
| レビュー観点 | P0 基準に限定。書けない指摘はレビュアー側で最初から台帳へ直行 |
| 範囲外の明示 | 差分の外にある既存構造はレビュー対象外。台帳で管理する |
| レビュアー | **種類の違う2系統**を当てる（盲点の非相関のため） |

## 3. 実測で確認した技術的事実

新しい backend を書くときに再発しうるもの。すべて実際に実行して確認した。

### `SecretStr`（pydantic 2.12.5 で確認）

```python
SecretStr("x") == "x"      # → False。例外を出さず常に False
SecretStr("x").strip()     # → AttributeError（こちらは気づける）
bool(SecretStr(""))        # → False。真偽値評価は正しく動く（__len__ を持つ）
```

`==` が静かに False になるため、**「本番で開発用デフォルト値のまま起動する」検査を
黙って無効化しうる**。`SecretStr` を導入するときは、テストを先に直して赤を確認してから
アプリを直すこと。

**「無名の一時値なら漏れない」は成立しない。**

```python
sink(secret.get_secret_value())   # 呼び出し先の引数がフレームローカルになる
                                  # → capture_locals=True の traceback に平文が載る
```

名前に束縛した場合との差は**出現回数**であって、漏れるか否かではない。
フレームローカル対策は呼び出し方の規律ではなく、**境界の側**で扱う。

`SecretStr` が効かないもの: 未宣言キーのタイポ（型が付かない。対策は
`errors(include_input=False)`）、下流で平文 `list[str]` / `bytes` に戻る経路。

### 例外連鎖

`raise X() from None` は `__suppress_context__` を立てるだけで `__context__` は残る。
**`except` の外で投げる**と `__context__` が最初から存在せず、ライブラリのフレームも
traceback に載らない。

```python
cause_name = None
try:
    return build_something()
except Exception as exc:
    cause_name = type(exc).__name__
    del exc
raise DomainError(message)   # ← except の外
```

### 漏えいシンクは4種類ある

| 種類 | 例 | 消えるか |
|---|---|---|
| プロセス出力 | stdout / stderr | 起動のたびに出る |
| ログファイル | **出力先は環境変数で変わる**。固定パスで見ると見逃す | 保持期間しだい |
| DB の行 | **一度書いたら消えない** | 消えない |
| HTTP レスポンスボディ | 未認証で到達できる面がある | クライアントに届く |

**4つ目を忘れやすい。** アプリが外部へ能動的に返す面も観測対象に入れること。
環境ガード（`if ENVIRONMENT == "development"` 等）を置いたら、
**そのガードの正しさを検証するテスト**も書く。

### `urlparse` は percent-decode しない

DSN やURIの往復一致を確認するときは `sqlalchemy.engine.make_url` を使う。
本番コードだけでなく、**テストハーネスにも同じ誤りが入りうる**。
