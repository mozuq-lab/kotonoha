# 秘匿処理を7回直して7回とも漏れた話 — 引き算の防御が収束しない理由

設定値に含まれるパスワードが、起動失敗時のログに平文で出ていた。塞いだ。次のレビューで別の入力形式で漏れているのが見つかった。塞いだ。また別の形で見つかった。これを7回繰り返した。

7回目に気づいたのは、自分が悪い設計に対して正しい努力を続けていたということだった。注意力の問題ではなく、防御の置き場所が構造的に間違っていた。同じ轍を踏む人が減るように、何が起きていたかを書き残しておく。

## 7回とも「別の入力の形」で漏れた

対象は、接続先URIを診断用にログへ出すための秘匿関数だった。`redis://user:password@host:6379` のような文字列から資格情報を伏せ、スキームとホストだけを残す。よくある処理だ。

指摘と修正の履歴を並べると形がはっきりする。

| 回 | 漏れた入力の形 |
|---|---|
| 1 | URIが例外メッセージに丸ごと埋まる |
| 2 | `//` を欠いた形（`redis:pw@host`）でパーサが資格情報をパス側に入れる |
| 3 | ポートが数値でない場合にパース処理自体が例外を投げる |
| 4 | IPv6のブラケットが落ちる／複数ホストが丸ごと伏せられる |
| 5 | ユーザー名が1文字だと、置換処理が診断メッセージを破壊する |
| 6 | `//` を欠きコロンを含む生の秘密で、コロンより前が平文で出る |
| 7 | クエリ文字列の資格情報（`redis://?password=SECRET`）が素通りする |

7回目は特に苦い。6回目の修正で「`unix:///` のような正当なURIを潰さないように」と早期リターンを足した。その早期リターンがクエリ文字列を素通りさせた。**自分の修正が次の穴を作っていた。**

## 引き算の防御は、入力空間が無限だから終わらない

7回の修正はすべて同じ形をしていた。任意の文字列を受け取り、危険な部分を特定して取り除く。指摘された入力形式に対処し、次の指摘でまた別の形式に対処する。

これは denylist だ。入力空間が無限なのに、事例を列挙して潰そうとしている。列挙は原理的に終わらない。7周やって終わらなかったのは当然で、70周やっても終わらない。

厄介なのは、この設計が進捗しているように見えることだ。毎回きちんと再現し、原因を特定し、テストを書き、直している。作業としては正しい。ただ、埋めているのは無限にある穴のうちの1つでしかない。

同種の失敗は秘匿処理に限らない。入力バリデーション、サニタイズ、フィルタ——「危険なものを除去する」という発想はすべてこの形をとる。SQLインジェクション対策が文字列エスケープからプレースホルダへ移ったのも、XSS対策がブラックリストからコンテキスト別エスケープへ移ったのも、同じ構造の問題を同じ方向で解いている。

## 足し算にすると、想定外の形が出力に載る余地が消える

反転させる。入力から引くのをやめ、**安全と確認できた部品だけで出力を組み立てる**。

具体的には、出力に使ってよいトークンを閉じた集合に限定した。ライブラリが定義済みのスキーム名、厳格な文法に完全一致したホストとポート、そして固定文字列。パス・クエリ・フラグメント・ユーザー情報は「有無」だけを出す。文法に1文字でも外れたら構造情報を一切出さない。

```
redis://user:pw@host:6379/0   → redis://<credentials>@host:6379/<path>
redis://?password=SECRET      → redis://<no host>?<query>
sk-ant-abc:def                → <URI: 解釈不能>
```

この設計だと、想定していない入力形式が来ても出力に載る余地がない。クエリ漏れもコロン漏れも `//` 欠落も、構造的に起こらない。24,000件の敵対的入力で試したところ、引き算版は6.5%で漏れ、足し算版は0件だった。

副次的な効果として、コードが184行から25行になった。置換処理のヒューリスティック——「パスワードが実在する単語だったらどうする」「パーセントエンコードされていたらどうする」——が丸ごと不要になったからだ。問題そのものを消せば、その問題のケース分析も消える。

## 修正の後に書いたテストは、修正が効く観測点を選んでしまう

ここからは、なぜ7回も気づかなかったのかという話になる。

毎回、回帰テストを書いていた。だから「もう漏れない」と報告できた。そのテストがこれだ。

```python
with pytest.raises(StorageError) as exc_info:
    build_client(f"scheme://:{secret}@host:6379")
assert secret not in str(exc_info.value)
```

一見まともに見える。実際には、直したばかりの唯一安全なチャネルだけを検証していた。

秘密が観測できる経路を後で数え直したら、8つあった。

| 経路 | 漏れていたか |
|---|---|
| `str(例外)` | なし ← テストが見ていたのはここだけ |
| 例外の `args` | なし |
| `__cause__` | **あり** |
| `repr(__cause__)` | **あり** |
| `__cause__.args` | **あり** |
| 連鎖トレースバック | **あり**（起動失敗時に標準エラー出力へ） |
| `exc_info` 付きログ | **あり** |
| オブジェクトグラフ | **あり** |

8つ中5つで漏れていた。緑のテストが、生きている漏えいを「対処済み」と証明していた。

原因ははっきりしている。**修正を書いた後にアサーション対象を選ぶと、無意識に修正が効く観測点を選ぶ。** これはテスト駆動開発が「先にテストを書き、失敗を目撃してから直す」を要求する理由そのものだ。順序を守らないと、テストは「この修正は正しい」ではなく「この修正はこの観測点では効く」しか証明しない。

## 有限な側を列挙し、無限な側を生成する

もう一つ、検証の設計を間違えていた。

秘密が漏れる経路（観測先）は有限だ。Pythonの例外から情報が外へ出る道は、文字列表現・例外連鎖・トレースバック・属性の推移閉包の4種類しかない。数えられる。

一方、入力は無限だ。URIの形は組み合わせで無数に作れる。

私は逆をやっていた。入力を事例で列挙し（指摘されたものだけ）、観測先は数えていなかった（1つだけ見ていた）。正しくは、観測先を列挙し、入力を生成する。

実装は難しくない。観測先を1つの関数に集約する。

```python
def observe(call, sentinel):
    """1回の呼び出しについて、有限個の観測面すべてを調べる"""
    # 戻り値 / str / args / __cause__ / __context__ /
    # 既定トレースバック / ローカル変数つきトレースバック /
    # ログ出力 / オブジェクトグラフの有界探索
```

この関数が「監査対象の全域」の定義になる。新しい出口が心配になったら、ここに1行足すだけで既存の全テストが自動的にその面を検査する。出口ごとに個別テストを書く必要がなくなる。

入力側は文法ベースで生成する。プロパティベーステストのライブラリを入れてもいいが、この種の問題では標準ライブラリの直積と固定シードの乱数で十分だった。スキーム名はライブラリの定義済み一覧から取る（手書きすると漏れる。実際、手書きで足した1つが存在しないスキーム名で、そこから漏れた）。

一点だけコツがある。検出用の目印は生成された長い一意文字列にする。`pass` や `host` のような短い辞書語を目印にすると `localhost` に `host` が含まれて偽陽性が出る。実運用の秘密は生成された一意文字列なので、部分一致による判定は現実的な脅威モデルと一致する。

## `from None` は連鎖を「抑制」するが「消さない」

細かいが、同じ罠の典型例なので書いておく。

例外を包み直すとき、元の例外に秘密が載っていると連鎖経由で漏れる。これを避けようとして `raise NewError(...) from None` と書いた。

これは効かない。`from None` が設定するのは `__suppress_context__` フラグだけで、`__context__` には元の例外が残る。標準のトレースバック表示はフラグを尊重するので見えなくなるが、`__context__` を辿るツールには筒抜けになる。

```python
try:
    ...
except Exception as exc:
    raise NewError("...") from None
# → __cause__ は None、__context__ には元の例外が残っている
```

確実に消すなら、`except` ブロックの外で投げる。

```python
detail = None
try:
    ...
except Exception as exc:
    detail = type(exc).__name__
    del exc
raise NewError(detail)   # ← except の外。__context__ が最初から存在しない
```

副次効果として、新しい例外のトレースバックにライブラリのフレームが載らなくなる。ローカル変数経由の漏えいも同時に消える。

**APIの名前は意図を表すが、機構を表すとは限らない。** `from None` は「連鎖を断つ」ように読めるが、実際には「表示を抑制する」だった。名前を信じずに機構を確かめる、という当たり前のことを7回目まで怠っていた。

## 「指摘ゼロ」は成果物の性質ではない

最後にプロセスの話を短く。

このループの停止条件を「レビューで指摘が出なくなること」に置いていた。これが間違いだった。指摘の数は成果物の性質ではなく、レビュアーの出力の性質だ。十分な探索予算があるレビューは、どんなコードに対しても必ず何かを見つける。とくに「この抽象は責務が多い」「この階層は使われ方と合っていない」といった設計上の指摘は反証不能で、いくらでも生成できる。

さらに悪いことに、毎回10件以上をまとめて直していたため、変更範囲が広がり、それが次の周の指摘を生んでいた。指摘数が測っていたのは残存欠陥の量ではない。直前の差分の面積だ。この状態では、欠陥が減っても指摘は減らない。

停止条件は成果物側で機械判定できるものに置く必要がある。私が採ったのは「実証済みの欠陥がゼロ」——実証済みの定義は「その指摘を赤にする自動テストが実際に書けたもの」——と「未分類の指摘がゼロ」の2つだ。後者は「指摘が0件」ではない。すべての指摘が「今直す/テストで固定する/記録して後回し/理由付きで却下」のいずれかに割り当てられていればよい。

## まとめ

7回の失敗から取り出せる一般則を3つ書いておく。

第一に、防御は入口に置く。出口を1つずつ守ると、防御は「値 × 出口」の直積に散らばる。出口は新しい呼び出しを足すたびに増えるので、この直積は終わらない。値の側で守れば、出口を数える作業そのものが消える。

第二に、安全と確認できたものだけで組み立てる。危険なものを取り除く書き方は無限の入力に対する列挙になるが、組み立てる書き方なら想定外が出力に載る余地が構造的に生じない。

第三が検証の設計で、ここが一番見落としやすい。観測先は数えられるが、入力は数えられない。有限な側を列挙し、無限な側を生成する。逆にすると、事例ベースのテストが、事例ベースの設計と同じ穴を抱えてしまう。

どれも新しい話ではない。SQLのプレースホルダも、テンプレートエンジンの自動エスケープも、型による不変条件の表現も、同じ方向を向いている。それでも自分の手元で7回踏んだ。**知っていることと、目の前のコードでそれを適用できることの間には、はっきり距離がある。**
