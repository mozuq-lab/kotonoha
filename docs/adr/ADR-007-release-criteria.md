# ADR-007: リリース基準 — 公式ストアで本公開。初回は AI 変換抜き。条件は 4 つで閉じる

状態: 承認済み（2026-08-29 決定、2026-08-30 目標日を廃止、2026-09-02 条件 3 を改訂、2026-09-06 書き直し。2 系統レビュー反映済み。署名: mozuq）／ 出自: ヒアリング 2 巡（2026-08-29）

## 背景と課題

是正計画（Phase 0〜5）には「利用者に届ける」工程が無く、放置すると内部品質工程が無限に続き、プロダクトの目的（発話困難な方が伝えられること）に接続されない。
frontend はオフラインファーストで、文字盤・TTS・定型文・履歴・お気に入り・緊急ボタンは backend 無しで動く。したがって「何を満たしたら届けるか」「backend を待つか」は計画全体の優先順位を決める決定である。
ヒアリング結果（2026-08-29）: 最初から一般公開する。特定の初期利用者は想定しない。使い勝手は届けながら確かめる（formative usability test はブロッカーにしない）。

## 制約

- 対象利用者は発話困難な方。サポート窓口を持たない一般公開では、**壊れたときに利用者自身が声で助けを求められない**前提で品質基準を置く
- ユーザーデータは端末内のみ（NFR-101）。会話内容はいかなる形でも送信しない
- 公式ストア配布には開発者登録（Apple Developer Program 年額 / Google Play 登録料）・審査・プライバシーポリシーの公開が要る
- 推奨デバイスは 9.7 インチ以上のタブレット。iPad を含むため App Store は必須経路

## 検討した選択肢

A. リリース工程を定義しない（現状維持。決定コストゼロ）／B. 身近な利用者・支援者経由の限定配布から始める（伴走しながら直せて formative test を兼ねられ、基準を低く始められる）／C. オープンテスト段階（Play オープンテスト / TestFlight 公開リンク）を挟む（「試験中」と明示して一般に届けられ、初期不具合の直撃を緩和できる）／D. **公式ストアでいきなり本公開する**（到達が最大で、届けながら確かめる方針と一致。採用）
品質フィードバック経路（1. 一切入れない／2. クラッシュ報告のみ＝アプリから送信／3. オプトインのクラッシュ報告／4. ストア標準に依拠しアプリからは送らない）は 2026-08-29 に案 2 を採ったが、2026-09-02 に案 4 へ移し、選定は **ADR-009** に委ねた。

## 決定

案 D。公式ストア（App Store / Google Play）でいきなり本公開する。**初回リリースは AI 変換抜き（backend 非依存）でよい。**リリース条件は次の 4 つで閉じ、**日付は置かない**（2026-08-30 に目標日を廃止）。**新しい条件を足すには本 ADR の改訂が要る**——作業中に見つかった問題は条件ではなく台帳（`docs/ledger.md`）へ送る。

1. frontend 品質フェーズ（是正計画の Phase 3）の完了条件をすべて満たす（永続化失敗の利用者通知・お気に入り 1 真実化・E2E 残す 4 経路が CI 緑・Hive 許可リスト）
2. 緊急ボタンの両側テストが緑（発報できないことと誤発報の両方を検査。B-2）
3. クラッシュ報告の方針が決まっており（**＝ADR-009**。ストア標準に依拠し、アプリからは何も送らない）、プライバシーポリシーに**本アプリがクラッシュ情報を送信しないこと**と、OS・ストアの診断機能により送られうる内容が明記されている（**2026-09-02 改訂**。旧文言「クラッシュ報告が導入済み（会話内容・入力内容・ハッシュを一切含まない）で、プライバシーポリシーに送信内容が明記されている」はアプリから送ることを前提にしていた）
4. ストア要件が揃っている: 開発者登録・プライバシーポリシー公開・審査通過／ストア記載で医療・治療効果を謳わない（コミュニケーション支援としてのみ説明する）／**サポート連絡先（ストア必須項目）を、クラッシュに映らない不具合の受付経路として運用し、月 1 でストアレビューとあわせて巡回する**（独立レビューの指摘: 本公開 × クラッシュ報告のみでは非クラッシュ不具合を誰も観測できない）

明示的に条件にしないもの: backend / AI 変換（後続リリースで追加する。**リリースは backend に依存しない**）／formative usability test（届けながら確かめる。接点ができたら行うがブロッカーにしない）／オープンテスト段階（挟まない。ただし Play の段階的公開＝本公開のままの % 展開は緩和策として使ってよい）。充足状況: 条件 1（PR #89。1b は PR #88、1c は Issue #84 / PR #87）・条件 2（PR #90）・条件 3（PR #91）は充足。**残るは条件 4** で、開発者登録と審査が未。**開発者登録（Apple Developer Program / Google Play）は純粋な暦時間でコード作業と並行できる**——意図的に後回しにしてある（2026-08-30 決定）が、クリティカルパスから外すため他の作業を待たずに開始すること（Apple の審査も日数を要しうる）。サポート連絡先は L-51、Android のアップロード鍵は L-52。

## 決定理由と却下案

- 案 A 却下: 「Phase 5 の先が無い」問題がそのまま残り、内部品質工程が無限に続く（実例: 2026-08-30 の E2E 修復で CI を 10 周回したが、その全てがテストの整備でアプリの不具合は 1 件も無かった。Issue #84——原因は初回チュートリアルのオーバーレイがタップを吸収していたことで、アプリの不具合ではなかった）
- 案 B 却下: 該当する相手が現状いない。相手探しがリリースの律速になる
- 案 C 却下: 本公開まで一段増える。試験中ラベルの分だけ届く範囲が狭まる
- **目標日を置くのをやめた**（2026-08-30。承認者 mozuq。同日中に「2026-10 末 → 2026-12 末（暫定）」への更新を 1 度行ったうえで、日付そのものを歯止めにしない判断に至った）: 判断は「リリース日時にこだわりはない」で、日付が実際の制約でないなら「2026-12 末（警報線）」と書いたまま実態が違う状態になる。これは本プロジェクトが繰り返し直してきた文書と実態の乖離そのもので、形骸化した警報線は無いほうがましである。日付が果たしていた歯止めは**条件 1〜4 の閉包**が引き継ぐ——日付が無いときの真のリスクは「条件が増えること」であり（2026-08-30 の作業だけで L-27〜L-30 の 4 件が見つかっている）、台帳送りを既定にし、条件への昇格を ADR 改訂という重い手続きに縛る
- 却下した削減案（日付を守るために検討したもの。**条件を増やしたくなったときの交換材料**として残す）。**A. お気に入り機能を初回から外す**: 残 Phase 3 の最大項目が丸ごと消え、lib 1,221 行・test 3,916 行を削減できる。統合すべき負債＝ 4 箇所への散在はお気に入りが存在するから発生しているので、外せば負債ごと消える。却下理由: 機能を利用者から取り上げる決定であり、要件 REQ-701〜704 の取り下げにあたる
- 削減案 **B. Android を初回から外す（iPadOS/iOS のみ）**: 外部律速（ストア登録・審査・実機テスト）が半減する。必須経路は iPad を含む App Store だけで、Google Play は必須ではない。却下理由: 対象利用者の一部に届かない
- 削減案 **C. 対面表示モード（526 行）・入力候補（377 行）を外す**: 効果が限定的で、払う対価に見合わない

## 限界

初期不具合が本番利用者に直撃しうる。当事者による事前検証は行わないので、B-2 観点（誤タップ・データ喪失・緊急ボタン。AGENTS.md 規律 6）は仮説のまま本番に出る。緩和は条件 1〜3 の品質バーとストアのクラッシュ集計だけである。クラッシュしない不具合（使いにくさ・誤操作誘発）はクラッシュ集計に映らず、条件 4 のサポート連絡先とストアレビューが唯一の受け皿になる。ADR-009 でアプリからの送信をやめたため、Dart 例外と Web のクラッシュも見えない。
条件 1 の括弧書き 4 項目と、是正計画の Phase 3 完了条件は範囲が食い違っていた（計画側は往復テストと OpenSpec の capability も含む。完了時に破棄される文書の中で条件を減らす判断をしたことになる）。2026-08-31 に両方とも実施したので実務上は解消したが、括弧書きを「Phase 3 完了条件の要約であって定義ではない」と読むか 4 項目を定義とするかは、まだ決めていない（どちらの読み方でも条件 1 は満たされる）。

## 検査

(i) 層 2 — 索引の「関わる行為」は権限・外部送信先で、それに触れる変更には `scripts/adr-touch.sh` が本 ADR の索引行を PR コメントとして貼る。
(iii) 条件の充足そのものを見る機械は無い。核の索引と層 3・月 1 の棚卸しだけである。条件 1〜3 はテストが固定する（Hive 許可リスト・往復テスト 4 本・緊急ボタンの両側）。条件 4 は台帳（L-51・L-52）で追う。AAB・mapping・ネイティブシンボルは #97 で解決済み。
条件 2 の両側は mutation で赤を実測して確かめた（誤発報側: 2 段階確認ダイアログ・`_isProcessing` の連打ガード・モーダル・「いいえ」「はい」の並び順／発報できない側: 全ルートでの表示とタップ到達性・チュートリアル表示中も手前・確認後に音が鳴る・音源アセットが実在し 0 バイトでない・タップターゲット 44px 以上・OS 音量 0 の警告）。そのとき「確認のみ」のはずが穴が 1 つ出た——「全画面共通」を謳う検査が 7 ルート中 4 ルートを手書きで回しており、`/favorites` `/help` `/face-to-face` はどの緊急ボタン検査も通っていなかった。**実装は正しく、壊れていたのは検査の側**。PR #90 で `router.configuration.routes`（アプリが実際に配信するルート＝権威）から列挙し、「見えている」ではなく「タップが届いて確認ダイアログが開く」ところまで縦向きとタブレット横持ちの両方で検査する形に変えた。**テスト側が対象の一覧を手書きすると、対象が増えたときに静かに検査から漏れる**（ADR-005 の検査条項で踏んだのと同じ形）。

## 再訪条件

データ喪失・緊急ボタン誤動作・会話内容の意図しない送信が**1 件でも報告されたら**、配信を一時停止して原因を特定するまで再開しない。
リリース条件を増やしたくなったら本 ADR を改訂する（その際は削減案 A・B を交換材料として検討する。条件を足すなら何かを削る）。
条件 1〜4 をすべて満たしても出さない判断をしたら、本 ADR の前提（届けながら確かめる）が崩れているので見直す。
伴走可能な当事者・支援者との接点ができたら、次リリースを案 B・C 経由にする部分的な回帰を検討してよい。
