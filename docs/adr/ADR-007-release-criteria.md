## コンテキスト

是正計画（Phase 0〜5）には「利用者に届ける」工程が無く、放置すると内部品質工程が
無限に続き、プロダクトの目的（発話困難な方が伝えられること）に接続されない。
frontend はオフラインファーストで、文字盤・TTS・定型文・履歴・お気に入り・緊急ボタンは
backend 無しで動作する。したがって「何を満たしたら届けるか」「backend を待つか」は
計画全体の優先順位を決める決定である。

ヒアリング結果（2026-08-29）: 最初から一般公開する。特定の初期利用者は想定しない。
使い勝手は届けながら確かめる（formative usability test はブロッカーにしない）。

### 制約条件

- 対象利用者は発話困難な方。サポート窓口を持たない一般公開では、
  **壊れたときに利用者自身が声で助けを求められない**前提で品質基準を置く
- ユーザーデータは端末内のみ（NFR-101）。会話内容はいかなる形でも送信しない
- 公式ストア配布には開発者登録（Apple Developer Program 年額 / Google Play 登録料）・
  審査・プライバシーポリシーの公開が必要
- 推奨デバイス 9.7 インチ以上のタブレット（iPad を含むため App Store は必須経路）

## 検討した選択肢

### 選択肢A: リリース工程を定義しない（現状維持）

- 長所: 決定コストゼロ
- 短所: 「Phase 5 の先が無い」問題がそのまま残る。是正計画が目的に接続されない

### 選択肢B: 身近な利用者・支援者経由の限定配布から始める

- 長所: 伴走しながら直せる。formative test を兼ねられる。基準を低く始められる
- 短所: 該当する相手が現状いない。相手探しがリリースの律速になる

### 選択肢C: オープンテスト段階（Play オープンテスト / TestFlight 公開リンク）を挟む

- 長所: 「試験中」と明示した上で一般に届けられ、初期不具合の直撃を緩和できる
- 短所: 本公開まで一段増える。試験中ラベルの分だけ届く範囲が狭まる

### 選択肢D: 公式ストアでいきなり本公開する（採用）

- 長所: 到達が最大。届けながら確かめる方針と一致
- 短所: 初期不具合が本番利用者に直撃する。品質条件とクラッシュ報告で緩和するしかない

### 品質フィードバック経路の選択肢

1. 一切入れない — 最もプライバシー主義だが、サイレントな不具合（データ喪失等）が永久に見えない
2. ~~**クラッシュ報告のみ（採用）**~~ — クラッシュ・致命的エラーのみ**送信**、入力内容ゼロ。
   **2026-09-02 に採用を取り下げた**（下記の選択肢4へ移した。ADR-009）
3. オプトインのクラッシュ報告 — 整合的だが同意率の分だけ盲目になる
4. **ストア標準に依拠し、アプリからは何も送らない（2026-09-02 採用。ADR-009）** —
   App Store Connect / Google Play Console のクラッシュ集計だけを使う。
   依存の追加ゼロ・外部送信先の追加ゼロ。**送信経路が存在しないので、
   会話内容が漏れることを表現できない。** 代償として Dart 例外と Web のクラッシュは見えない

## 決定

**公式ストア（App Store / Google Play）でいきなり本公開する。初回リリースは
AI変換抜き（backend 非依存）でよい。品質フィードバックはクラッシュ報告のみ入れる。**
（**2026-09-02 改訂**: そのクラッシュ報告は**ストア標準に依拠し、アプリからは何も
送らない**形とした。ADR-009）

リリース条件（すべて機械的・確認可能）:

1. frontend 品質フェーズ（是正計画の現 Phase 3）の完了条件をすべて満たす
   （永続化失敗の利用者通知・お気に入り1真実化・E2E 残す4経路が CI 緑・Hive 許可リスト）
2. 緊急ボタンの両側テストが緑（発報できないことと誤発報の両方を検査。B-2）
3. クラッシュ報告の方針が決まっており（**ADR-009**: ストア標準に依拠し、アプリからは
   何も送らない）、プライバシーポリシーに**本アプリがクラッシュ情報を送信しないこと**と、
   OS／ストアの診断機能により送られうる内容が明記されている
   （**2026-09-02 改訂**。旧文言「クラッシュ報告が導入済み（会話内容・入力内容・
   ハッシュを一切含まない）で、プライバシーポリシーに送信内容が明記されている」は
   アプリから送ることを前提にしていた。経緯は ADR-009）
4. ストア要件が揃っている: 開発者登録・プライバシーポリシー公開・審査通過。
   ストア記載で医療・治療効果を謳わない（コミュニケーション支援としてのみ説明する）。
   **サポート連絡先（ストア必須項目）を、クラッシュに映らない不具合の受付経路として
   運用し、月1でストアレビューとあわせて巡回する**（Phase 4 の棚卸しと同周期。
   独立レビューの指摘: 本公開×クラッシュ報告のみでは非クラッシュ不具合を誰も観測できない）
5. **リリース条件は上の1〜4で閉じている。日付は置かない。**
   **新しい条件を足すには本 ADR の改訂が要る。**（2026-08-30 に目標日を廃止。
   経緯は下記「目標日を廃止し、条件の閉包を歯止めにする」）

明示的にリリース条件にしないもの:

- backend / AI 変換（後続リリースで追加する。**リリースは backend に依存しない**）
- formative usability test（届けながら確かめる。接点ができたら行うが、ブロッカーにしない）
- オープンテスト段階（挟まない。ただし Play の段階的公開（本公開のままの % 展開）は
  緩和策として使ってよい）

受け入れるトレードオフ: 初期不具合が本番利用者に直撃しうる。緩和はリリース条件
1〜3 の品質バーとクラッシュ報告であり、当事者による事前検証は行わない。

## 目標日を廃止し、条件の閉包を歯止めにする（2026-08-30）

**目標日を置くのをやめた。** 承認者: mozuq。
経緯として、同日中に「2026-10 末 → 2026-12 末（暫定）」への更新を1度行い、
そのうえで**日付そのものを歯止めにしない**判断に至った。

### なぜ日付をやめたか

承認者の判断は「リリース日時にこだわりはない」。日付が実際の制約でないなら、
**ADR に「2026-12 末（警報線）」と書いたまま実態が違う状態**になる。
これは本プロジェクトが繰り返し直してきた「文書と実態の乖離」そのもので、
形骸化した警報線は無いほうがましである。

### 日付が果たしていた役割を、何が引き継ぐか

本 ADR は次の理由で書かれた（「コンテキスト」節）。

> 是正計画には「利用者に届ける」工程が無く、**放置すると内部品質工程が無限に続き**、
> プロダクトの目的に接続されない

日付はその歯止めだった。実例もある——2026-08-30 の E2E 修復では CI を10周回したが、
**その全てがテストの整備であり、アプリの不具合は1件も無かった**（Issue #84）。
価値が無かったわけではないが、この種の作業は放置すれば際限なく続く。

日付を外す以上、別の歯止めが要る。**条件1〜4の閉包**がそれである。

- **リリース条件は1〜4で閉じている。**これを満たせば出す
- **新しい条件を足すには本 ADR の改訂が要る。**改訂には却下案の記録を伴う
- 作業中に見つかった問題は、**リリース条件ではなく台帳（Issue #85）へ送る**

**日付が無いときの真のリスクは「条件が増えること」である。**
実際 2026-08-30 の作業だけで L-27〜L-30 の4件が見つかっている。
これらが「リリース前に直すべき」として条件へ流れ込むと終わらない。
台帳へ送ることを既定にし、条件への昇格を ADR 改訂という重い手続きに縛る。

### 条件2 を確認した（2026-08-31）

**「確認のみ」と書いていたが、確認したら「発報できない」側に穴が1つあった。**

まず件数を測り直した。**緊急ボタン関連のテストは 176件**で、本 ADR が
繰り返し書いていた「157件」は古い数字だった（文書の数字は使う前に測ること）。

両側それぞれを、**mutation で赤を実測して**確かめた。

| 側 | 何が守っているか | 実測した mutation |
|---|---|---|
| **誤発報** | 2段階確認（ダイアログ）／`_isProcessing` による連打ガード／モーダル（ダイアログ外タップで閉じない）／「いいえ」「はい」の並び順 | 2段階確認を外して1タップで発報させる → 赤 |
| **発報できない** | 全ルートでの表示と**タップ到達性**／チュートリアル表示中も手前／確認後に音が鳴る／音源アセットが実在し0バイトでない／タップターゲット44px以上／OS音量0の警告 | 確認後に音を鳴らさない → 赤／44px保証を外す → 赤／チュートリアル中にタップを吸収させる → 赤／1画面だけ緊急ボタンを消す → 赤／横向きだけタップを吸収させる → 赤 |

**見つけた穴**: 「全画面共通」を謳う検査が、**7ルート中4ルートを手書きで回していた**。
`/favorites` `/help` `/face-to-face` はどの緊急ボタン検査も通っていなかった。
**実装は正しく、壊れていたのは検査の側**（全7ルートで緑になることを実測）。
手書きの一覧をやめ、`router.configuration.routes`（アプリが実際に配信するルート＝権威）
から列挙する形に変え、あわせて「見えている」ではなく「**タップが届いて確認ダイアログが
開く**」ところまで、縦向きとタブレット横持ちの両方で検査するようにした。

**この穴は ADR-005 の「検査」条項で踏んだものと同じ形である**——テスト側が対象の一覧を
手書きすると、対象が増えたときに静かに検査から漏れる。権威から列挙すること。

#### 条件1 の範囲に食い違いがあったことの記録

条件1 は「Phase 3 の完了条件をすべて満たす」であり、括弧書きは4項目を挙げている。
一方、是正計画の Phase 3 完了条件には**往復テストと OpenSpec の capability も
含まれている**。Phase 3 の計画書はこの2つを「リリース条件に入っていない」と
書いていたが、**それは完了時に破棄される文書の中で条件を減らす判断をしたことになる**
（本 ADR は条件の増減に改訂を要求している）。

**2026-08-31 に両方とも実施したので、この食い違いは実務上は解消した。**
括弧書きを「Phase 3 完了条件の要約であって定義ではない」と読むか、
4項目を条件の定義とするかは、**次に本 ADR を改訂するときに決めること。**
いま決める必要は無い（どちらの読み方でも条件1は満たされている）。

## 結果・影響

### ポジティブな影響

- 是正計画に終点（利用者に届く）が接続され、優先順位が明確になる
- **Phase 順序を 1（ゲート）→ 3（frontend）→ 2（backend）に変更する根拠になる**
  （リリースのクリティカルパスは frontend のみ。計画の順序変更は Phase 0 の締めで反映）
- B-2 観点（誤タップ・データ喪失・緊急ボタン）がリリース条件として実効化する

### ネガティブな影響・リスク

- 当事者検証なしの一般公開: B-2 は仮説のまま本番に出る。クラッシュしない不具合
  （使いにくさ・誤操作誘発）はクラッシュ報告では見えず、ストアレビュー頼みになる
- クラッシュ報告の導入は**依存追加＋外部送信先の追加**であり、負債ゲート2項目に
  該当する。ツール選定・送信内容の上限は導入時に別 ADR で決める（ゲートを正規の
  入口として通す）。「端末内完結」の説明はプライバシーポリシーで
  「クラッシュ情報のみ送信」に更新が必要
- ストア審査・開発者登録という外部律速が入る（Apple は日数を要しうる）

### 撤回条件

- データ喪失・緊急ボタン誤動作・会話内容の意図しない送信が**1件でも報告されたら**、
  配信を一時停止して原因を特定するまで再開しない
- **リリース条件を増やしたくなった場合、本 ADR を改訂する。**その際は
  上の削減案A・Bを交換材料として検討する（条件を足すなら何かを削る）
- 条件1〜4をすべて満たしても出さない判断をした場合、本 ADR の前提
  （届けながら確かめる）が崩れているので見直す
- 初期利用者から伴走可能な当事者・支援者との接点ができた場合、選択肢B/C への
  部分的な回帰（次リリースをテスト段階経由にする）を検討してよい

## 置き換えるADR

なし（ADR-001〜006 とは補完関係。ADR-001 の「ユーザー由来の内容を載せない」原則は
クラッシュ報告にもそのまま適用される）
