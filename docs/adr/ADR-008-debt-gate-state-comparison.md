# ADR-008: 負債ゲートは状態比較でブロックし、パターン照合は助言に留める

状態: **ドラフト（2026-08-29、署名: 未署名）** ／ 日付: 2026-08-29

## 背景と課題

Phase 1 で負債ゲートを実装した（コミット `d6f86718973`）。7項目を **差分の行に対する
パターン照合**（正規表現＋一部 AST）で検出する形である。

2系統の独立レビュー（Claude / Codex）が約20件を指摘し、**全件をこちらで再現した**。
中心は「**有効な別の書き方で素通しする**」ことだった。実測:

| 書き方 | 結果 |
|---|---|
| `pubspec.yaml` の依存を 2スペース indent で追加 | 検出する |
| 同じ依存を **4スペース** indent で追加 | **検出しない** |
| `Info.plist` に `<key>NSMicrophoneUsageDescription</key>` | 検出する |
| 同じキーを `<key\n>` と**タグ改行**で書く | **検出しない** |
| `client = Client()` | 検出する |
| `CLIENT = Client()`（大文字名） | **検出しない** |
| `register_provider()`（モジュール直下） | 検出する |
| `for p in PROVIDERS: register_provider(p)` | **検出しない** |
| `app.add_api_route(...)` | 検出する |
| `app.add_route(...)`（FastAPI が継承する有効な API） | **検出しない** |

**これを1つずつ塞ぐのは、8周の失敗と同じ形である。** 8周は「秘匿すべき URI の**形**」を
1つずつ潰して収束しなかった。今回は「負債を作るコードの**書き方**」を1つずつ潰すことになる。
どちらも入力空間が無限なので終わらない。

さらに、この実装は `docs/verification-principles.md`（L39）に反していた。

> 検証は最も外側の境界で行う——プロセスの stdout/stderr、実際の DB 行、
> HTTP レスポンスボディ、描画されたウィジェット。**戻り値だけを見るテストは、
> その関数が正しいことしか言わない。**

**差分の文字列**を見て、**結果の状態**を見ていない。ここで言う「戻り値だけを見る」に
あたるのが、パターン照合における「差分の行だけを見る」である。

偽陽性も実測で在庫がある（既存コード全体に当てた件数）:

| 規則 | 件数 | 中身 |
|---|---|---|
| `persistence` | **200** | frontend テスト 138（`Hive.registerAdapter` の並び）／読み取り専用の `open(..., "r")`／ゲート自身が3ファイル |
| `http_route` | 14 | うち2件はゲート自身のテストコード |
| `secret_config` | 3 | すべて誤検知（`"SecretStr" in text` が import 行・docstring に当たる） |

**放置すると何が起きるか。** Phase 3 の完了条件は「往復テストが4 feature に存在」だが、
Hive を使うテストを書くたびにゲートが止める。ADR-005 を機械的に貼る運用になり、
引用が意味を失い、最終的にゲートが外される。8周の環境条件（本流が動かないと
迂回の圧力がかかる）が再現する。

### 制約条件

- ゲートの目的は「**実装担当が ADR を読まずに書き始める**」ことを止めること（計画 §5 C層）。
  計画は既に「**既知の入口を検出する補助**であって、負債の網羅ではない」（L497）と明記している。
  ここから導かれる前提として、**敵対的な回避者は脅威モデルではない**——
  したがって「完全な網羅」は要件ではない
- 恒久成果物を工程記録にしない（計画 Phase 5 の判断基準）
- 状態比較の一部はアプリを動かす必要があり、**編集のたびには回せない**
- OpenAPI のパス集合は Phase 2 の新 backend、Hive 許可リストは Phase 3 まで素材が揃わない
- ゲート自身が負債になってはならない。規則を増やし続ける設計は、それ自体が保守対象になる

## 検討した選択肢

1. **現状維持** — 7項目のパターン照合を保ち、見つかった見逃しを都度埋める
2. **ゲートを廃止** — 層1（着手前の影響範囲）・層3（差分レビュー）・層5（棚卸し）に任せる
3. **ブロックは状態比較のみ。パターン照合は助言へ降格**（採用）
4. **全項目を AST・構文解析まで上げる** — 正規表現をやめ、各フォーマットの構文木で判定する

## 決定

案3。**ブロックする検査は「書き換えに閉じている」ものだけにする。**

### ブロックする検査（正規パーサで読む → 集合にする → **許可リストと比べる**）

**「前後を比べる」ではなく「現在の状態を、コミットされた許可リストと比べる」。**
`before` を取る必要が無くなるため、**基準の取り方に起因する失敗モードが構造的に消える**——
初回実装は merge-base と base 先端を取り違えて実在の dependabot ブランチを誤検出し、
git の失敗を「変更ファイルなし」に畳んで CI を緑にした。どちらも「前の状態を git から
取る」ことに由来する。許可リスト方式は **git を一切使わない**（作業ツリーと
コミット済みファイルの比較だけ）ので、この系統の欠陥が発生しない。

副次的な利点として、**ADR の引用が項目そのものに束縛される**。
「この依存は ADR-00X が許す」という主張が許可リストの行として残り、
レビュアーが個別に検証できる。初回実装の「コミットメッセージに ADR 番号があれば
PR 全体が通る」形にはならない。


| 項目 | 状態の取り方 | 入る Phase |
|---|---|---|
| 依存の追加 | `pubspec.yaml` を YAML パーサで、`requirements*.txt` を解析して**パッケージ名の集合**に | 1 |
| モバイル権限 | `Info.plist` を plist パーサ、`AndroidManifest.xml` を XML パーサで**キー集合**に | 1 |
| 設定キー | `.env.example` の**全キー集合**（Phase 1）→ `RuntimeConfig` のフィールド集合（Phase 2）。「秘密かどうか」の名前判定はしない——判定を挟むと `URI`/`URL`/`DSN` を落とす（初回実装の欠陥）。**全キーを許可リストで持つ方が、狭くて漏れる判定より良い** | 1 → 2 |

**保証の範囲は「フォーマットの内側」であって「すべて」ではない**（2系統の独立レビューで
一度過大に書いて訂正した）。閉じているのは次の2つに対してだけである。

1. **そのフォーマットの書き方**（indent 幅・タグの改行・行順・コメント・引用符・
   `export` 前置き・extras・範囲指定・環境マーカー）
2. **識別子に含めた出どころ**（セクション・flavor・供給元・ファイル）

閉じていないもの:

- **正規パーサが無いフォーマット。** `ios/Podfile`（Ruby DSL）と
  `android/**/build.gradle.kts`（Kotlin DSL）のネイティブ依存は**対象外**。
  regex で足すと段階4に戻るので足さない。台帳へ送る
- **識別子に含めなかった属性。** 何を identity にするかは設計判断であり、
  粗すぎると「既存名のまま面が広がる」変更を見逃す。実際、初版は名前だけを鍵にして
  `dev_dependencies` → `dependencies` の昇格と供給元の差し替えを見逃した
- **Phase 2 の公開ルートはパスだけでは閉じない。** 既存パスに `POST` を足す変更が
  素通しするため、`(パス, メソッド)` を identity にする（独立レビューの指摘）
| モジュール副作用 | **境界を封じた import smoke**。実際に `import app.main` して副作用を観測する | 2 |
| 公開ルート | `app.openapi()` を実行して**パス集合**を取り、許可リストと比べる | 2 |
| 永続化面（Hive） | `typeId` ＋ 永続フィールドの**許可リスト** | 3 |

うち下3つは、**計画が既に指定していた検査**である（Phase 1「OpenAPI のパス数」L492、
Phase 2「subprocess import smoke」L604、Phase 3「Hive スキーマの許可リスト」L779。いずれも現物で確認済み）。
新しい発明ではなく、計画に書いてあった形へ戻す。

### 助言に降格する検査（ブロックしない）

- **外部送信先** — 送信先は実行時に設定から組み立てられるため、静的には閉じない
- 上記のうち、そのフェーズでまだ素材が揃わない項目の暫定パターン

助言は**漏れる前提**で運用する。受け皿は層1（着手前の影響範囲）と層3（差分レビュー）で、
どちらも計画に既にある。

**助言は CI のログに出す。`PostToolUse` フックは置かない。**
ブロックしないフックは、編集のたびに読まれない出力を積むだけになる。
「書いた瞬間に返す」ことの価値は、返した内容で**手が止まる**ことにあり、
止まらないなら出力の置き場所は CI で足りる。

### 面を消したら許可も消す

**許可リストは現在の状態と一致していなければならない。** 面が無いのに許可だけ残っていたら落とす。

残すと「削除 → 許可だけ残る → **ADR 無しで再導入できる**」経路が開く。Phase 2 は
`sqlalchemy` `redis` を消すので、放置すると ADR-001 / ADR-002 の守りが**削除の直後に
無効化される**（独立レビューの指摘）。直し方は許可リストから1行消すだけなので、
削除作業を止める負担にはならない。

### 受け入れるトレードオフ

- **「書いた瞬間に止まる」を諦める。** 状態比較は重く、編集のたびには回せない。
  ブロックは CI のみになる
- **`PostToolUse` フックを持たない。** 計画 §5「なぜ CI だけでは足りないか」が挙げた
  「フックを持たない経路（別ツール・手作業）を CI が拾う」という二重の網は、
  **CI 単独の一重**になる。編集から検出までの遅れを受け入れる
- **見逃しは残る。** 助言側は網羅しない

## 決定理由（却下した案と理由）

- **案1を却下**: 見逃しの列挙は終わらない。実測で、有効な別表記が7項目中6項目に存在した。
  **これは8周と同じ形であり、同じ理由で収束しない**
- **案2を却下**: 「ADR は pull（読みに行く）、失敗は push（読まずに始まる）」という C層の
  根拠は今も生きている。必要なのは**漏れない検査が数個**であって、**漏れる検査が7個**ではない。
  ただし撤回条件（下記）に触れたらこの案へ戻す
- **案4を却下**: AST は**整形には閉じているが意味には閉じていない**。実測で
  `for` ループ・デコレータ・反転 main guard・大文字名が素通しした。段を1つ上げても
  列挙ゲームは終わらない。**同じ労力を状態比較に払えば、そのフォーマットの内側では閉じる**

**分かれ目は「書き換えに閉じているか」である。**

| 段階 | やり方 | 何に対して閉じているか |
|---|---|---|
| 1. 実行して観測 | OpenAPI のパス集合／import smoke | **コードの書き方すべて** |
| 2. 成果物をパーサで読む | `pubspec.lock` / plist / XML / pydantic の `model_fields` | **そのフォーマットの書き方すべて** |
| 3. ソースを AST で読む | `ast.parse` してノード種別を見る | 整形には閉じるが**意味には閉じない** |
| 4. 差分の行をパターン照合 | 正規表現 | **何に対しても閉じない** |

現行実装は3〜4段目にある。ブロックする検査を1〜2段目に上げる。

## 影響

### ポジティブ

- **パーサが読むフォーマットの内側では**「11通り目の書き方」が存在しない。
  そのフォーマットについては見逃しを埋める作業が終わる
- 偽陽性を直す作業は**有限**で、既存コードに当てれば**今日測れる**（現在 persistence 200件）。
  見逃しと違って終わりがある
- 計画が既に指定していた検査が、ゲートの本体になる。二重に作らずに済む

### ネガティブ・リスク

- **素材が揃うまでブロックできる項目が少ない。** Phase 1 時点では依存・モバイル権限・
  `.env.example` の3つに留まる。OpenAPI と import smoke は Phase 2、Hive は Phase 3
- **「書いた瞬間に止まる」設計を諦める**（計画 §5「なぜ CI だけでは足りないか」の前提が弱まる）。
  検出は PR 時まで遅れ、既に書き終えたコードへの差し戻しになる。
  これは計画が「CI まで届くと、それは既に書き終えたコードへの差し戻しになる」として
  避けようとした状態そのものであり、**意図的に受け入れる後退**である
- **この決定自身、ゲートの守りを持たない。** ゲートの設定を弱める変更
  （`.claude/settings.json` / `.github/workflows/debt-gate.yml` の編集）はゲートに掛からず、
  CODEOWNERS も無い。**ここは仕組みで防げていない**と明示しておく。Phase 4 の棚卸しで拾う

### 撤回条件

- **Phase 3 終了時点で、状態比較の検査が3項目以下しか動いていない** → 案2（ゲート廃止）へ戻す。
  「漏れない検査が数個」が実現しないなら、C層を維持する根拠が無い
- **ブロックする検査の偽陽性で開発が止まった** → その項目を助言へ降格する。
  ブロックの資格は「閉じていること」と「偽陽性が無いこと」の両方である

## 既存実装の扱いと、新実装が最初から満たすこと

**コミット `d6f86718973` は revert する。** 段階的に直すより小さい——ブロックする検査は
すべて作り直しになり、残るのは助言側の一部だけだからである（Phase 2 で backend を
「直す」のではなく「書き直す」と決めたのと同じ判断）。

レビューで出た指摘のうち、パターン照合と無関係な**純粋なバグ**は revert で消えるが、
**新実装が同じ形を再生産しないよう、最初から満たす条件として書き留める。**

| 旧実装の欠陥 | 新実装が満たすこと |
|---|---|
| 差分の基準が **merge-base と base 先端で混在**し、実在の dependabot ブランチを新規依存と誤検出した | 前後の状態は**同一の基準**から取る。PR では merge-base 対 head |
| **git の失敗が「変更ファイルなし」に畳まれ CI が緑になった**（fail-open） | 状態が**取得できなかったこと**と**変化が無かったこと**を区別する。取得失敗は落とす |
| **ADR 引用が実在番号を検査していなかった**（`ADR-999` で通る） | 引用は `docs/adr/` のファイル集合と突き合わせる。**この検査自体は閉じている** |
| リポジトリ外のファイルでフックが発火した | フックを置かないため消滅する |

これらは**新実装の受け入れ条件**であり、検査として書く（`docs/verification-principles.md`
B-3「過去に起きた欠陥の形」）。

## 起案時に判断を仰いだ点と、その回答

| 論点 | 回答（2026-08-29） |
|---|---|
| 既存コミット `d6f86718973` を revert するか、上に修正を積むか | **revert する** |
| `PostToolUse` フックを助言として残すか、削除するか | **削除する** |
| 撤回条件の閾値「Phase 3 終了時点で3項目以下」は妥当か | **3項目以下でよい** |

**「項目」の数え方**（独立レビューが曖昧さを指摘したので固定する）: 上の
**ブロックする検査の表の行数**で数える。現在は依存・モバイル権限・設定キーの **3**
（実装上の検査は5本だが、表では3行）。Phase 2 で公開ルートと import 副作用、
Phase 3 で Hive が入って **6** になる想定である。**いまは撤回条件の閾値に接している。**

## 置き換える ADR

なし。ADR-004（設定は不変）・ADR-005（1概念1真実）・ADR-006（レイヤ依存）は、
**ゲートが守る対象**であって、ゲートの作り方を定めるものではない。本 ADR はそれらを
変更しない。
