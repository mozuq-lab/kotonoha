# ADR-002: 本番は Workers 標準の概算レート制限、全体は AI Gateway

状態: 承認済み（2026-10-31、人がコスト削減のため TypeScript Worker と A 案を選択）。Workers への本番切り替えは未実施。

## 目的と制約

- 主目的は単一送信元の暴走・burst の抑制。副目的は粗い DoS 緩和。利用者間の公平性は非目標。
- IP ごとの制限では総費用を縛れない。全体の回数・支出は AI Gateway でも制限する。
- 支出制限はトークンと料金による推計・結果整合で、厳密な請求上限ではない。
- 公開済みアプリの URL・共通端末キー・HTTP 入出力を維持する。共通キーだけを制限の識別子にすると全利用者が枠を共有するので使わない。
- 入力・応答・IP・識別子を独自のログや DB に保存しない。識別子の扱いは公開文に告げる。

## 決定

- 本番は `backend/worker/src/` の TypeScript Worker。Containers を呼ばず、標準 Rate Limiting binding を使う。
- 変換と再生成それぞれ 12 回/60 秒を設定する。拠点ごとの概算制限であり、更新の遅れや分の切り替えで設定回数を超える場合を受け入れる。
- `CF-Connecting-IP` だけを採用し、利用者の XFF は読まない。IPv4 射影は IPv4、IPv6 は /64 にそろえる。
- API・送信元・UTC の分から、API_KEYS を鍵とする HMAC 識別子を作る。標準制限にはこの識別子だけを渡し、1 分ごとに切り替える。IP・識別子を AI の入力やヘッダーには載せない。
- binding は残り秒数を返さないので、429 の Retry-After と既存 X-RateLimit-* は最大 60 秒を案内する。成功時は付けない。
- Workers AI の同じモデルへ同じ REST API から送る。Gateway 必須、ログ収集・キャッシュを要求ごとに無効化。出力は 256 トークン。
- 既存の Container DO はこの変更で破壊せず、互換 export を残す。旧コンテナの削除と費用停止の確認は、API の切り替え確認後に人が行う。
- `backend/fastapi/` の旧 FastAPI は開発・比較用に残る。そちらの MemoryStorage・単一 worker ガードは従来どおりだが、本番の制限方式ではない。

## 以前の却下を変えた理由

2026-10-17 の版は「Rate Limiting binding は拠点ごとで、IP をキーにすることを勧めていない」として採らなかった。公式文書の勧めは 2026-10-31 に確かめた時点でも同じで、理由は IP が多くの利用者に共有され、意図より広く制限し得ることにある。次の理由で判断を変える。

- IP 共有の巻き込みは binding 固有ではない。旧実装も IP ごと 12 回/60 秒で、同じ限界を受け入れていた。
- 同じ IP は通常 1 つの拠点に届くので、拠点ごとのずれは経路が変わるときに限られる。主目的は連打の抑制で、厳密な数は要らない。
- 全拠点で正確に数えられる Durable Objects は、メモリだけで数える形でも IP 共有の限界と識別子の受け渡しが残る。新しいクラスを足すと `wrangler rollback` で旧版へ戻せなくなる。比べたうえで人が標準機能を選んだ（2026-10-31）。

## 却下した案

- Redis 等の共有ストア: 秘密入り URI が以前のレビュー往復の再生産源だった。今回も別の保存基盤を持つ必要がない。
- Durable Objects の永続カウンタ: 全拠点で正確に数えられるが、保存する識別子・稼働と保存の費用・実装が増える。今回の目的は費用削減と粗い連打抑制で、正確さを必要としない。
- 端末ごとの匿名 ID で数える: IP 共有の巻き込みは減るが、公開済みの版は ID を送らず、ID を変えるだけで制限を逃れられ、端末の外へ出る情報も増える。
- Worker のグローバル変数だけで数える: isolate 間で共有されず、同じ送信元でも枠が分かれる。
- AI Gateway だけ: 一人の連打が全体の枠を消費しやすく、単一送信元の抑制を失う。
- WAF だけ: 既存 workers.dev URL も同じように守る必要がある。binding を API の直前で使う方が経路をそろえられる。
- 単一 Containers + MemoryStorage の継続: 2026-10-03 時点では採用済み実装をリリース前に変える利益がなかった。今回は公開後の待機費用削減が人の依頼なので判断を変更する。

## 限界と検査

- 共通キーはアプリから取り出され得る。多数 IP による全体枠の消費と、同じ IP の利用者が枠を共有する限界は以前と同じ。オフラインの機能は影響を受けない。
- `backend/worker/test/api.test.mjs` は本番 Wrangler 構成・実 workerd・実 binding・HTTP で、認証順序、本文上限、送信元と API ごとの枠、IPv6 /64、AI に載せない項目、429 の外部契約を検証する。AI の通信境界だけが偽物。
- CI は Worker の型・HTTP 試験・deploy dry-run。分散拠点間の挙動と実サービスの費用はローカル試験では再現しない。
- 既存 Gateway の設定（2026-10-18、人の確認）: 支出 1 ドル/月、200 リクエスト/5 分、ログ収集オフ。支出制限の Workers AI に対する実際の遮断は未確認。本番切り替え時に確認する。

再訪: 実測で連打抑制が足りない、または全拠点での厳密な枠が必要になったときに Durable Objects と比べる。
