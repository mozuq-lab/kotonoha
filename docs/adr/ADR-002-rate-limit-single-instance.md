# ADR-002: レート制限は単一インスタンス前提。カウンタはプロセス内メモリ

状態: 承認済み（2026-08-29 決定、2026-09-02 実装で改訂、2026-09-06 書き直し。署名: mozuq）／ 出自: 是正計画 §3 決定2

## 背景と課題

`RATE_LIMIT_STORAGE_URI`（Redis 前提の共有ストア設定）が、8 周のレビュー往復のうち 7 周を占めた秘匿機構 `redact_storage_uri`（約 184 行）の存在理由だった。独立レビューはブランチ最終版にもなお漏えい（netloc の無い URI のクエリ資格情報が素通し）を発見しており、「秘密を URI に埋めて第三者ライブラリへ渡す」形は注意深さでは閉じない。秘匿が不要になる理由の残り半分は ADR-003（エラーは型）にある。
さらに、レート制限が根拠として引用してきた NFR-101 は「会話内容の端末内保存」の要件であり、レート制限の要件はどの要件書にも存在しなかった（独立レビューの発見）。何を守るのかが決まらないまま、守り方（共有ストア）だけが先に実装されていた。

## 制約

- 守るもの（主）: 単一送信元（IP）の暴走・burst の抑制。誤動作クライアントや漏れた端末キーの連打が、そのままプロバイダへ流れることを防ぐ
- 守るもの（副）: 粗い DoS 緩和
- 総費用の上限はレート制限では作れない（独立レビューの反例: N 個の送信元 IP から使えば per-IP 制限は総量を縛らない）。総費用の真の上限は AI プロバイダ側の支出上限（ハードリミット）であり、その設定を backend 公開日の必須条件とする
- 非目標: 利用者間の公平性。想定利用は単一端末で、多数利用者の競合はまだ無い
- 既定値は現行踏襲。1 リクエスト/10 秒/IP（`RATE_LIMIT_TIMES` / `RATE_LIMIT_SECONDS`）。守る対象の定義は本 ADR が正本で、`docs/design/kotonoha/api-endpoints.md` に残る NFR-101 引用は正本整理で本 ADR への参照に差し替える

## 検討した選択肢

1. Redis 等の共有ストアで複数インスタンス対応
2. **プロセス内メモリで単一インスタンス前提**（採用）
3. アプリ内レート制限を持たず、インフラ層（WAF / API Gateway）＋プロバイダ支出上限に任せる
4. レート制限なし

## 決定

案 2。`redis` 依存を削除し、`RATE_LIMIT_STORAGE_URI` という設定キー自体を作らない。秘匿すべき文字が 1 文字も無いので、秘匿機構ごと不要になる。
slowapi を外したので `memory://` という URI も存在しなくなり、`limits` の `MemoryStorage` を直接使う（2026-09-02、Phase 2 実装。計画 D2）。守る対象と単一インスタンス前提は変わらない。
uvicorn は `--no-proxy-headers` で起動し、XFF の解釈は `backend/app/ratelimit.py` の 1 箇所に閉じる。
`TRUSTED_PROXY_COUNT`（既定 0）は実段数と一致させる。0 なら `X-Forwarded-For` を一切信頼せず接続元 IP を使い、1 以上なら XFF の右から N 番目を採り、チェーンが段数に満たなければ偽装を避けて接続元 IP へフォールバックする。

## 決定理由と却下案

- 案 1 却下: 秘密入り URI が 7 周の再生産源。利用者ゼロで、必要になる規模に無い。**復帰条件**: 実測でマルチインスタンスが必要になり、かつ資格情報を URI に埋めない方式（ElastiCache IAM 認証等）を採る場合に限る
- 案 3 は却下ではなく保留: 今日はインフラが存在せず検証できない。デプロイ形態の ADR で第一候補として再評価し、採用するならアプリ内カウンタは削除まで戻す
- 案 4 却下: 端末 API キーの漏えいや誤動作クライアントに対して費用が無防備になる

## 限界

同一コンテナ内の worker>1 は起動ガードで落ちるが、**replica は検出できない**（single-worker × 2 replica は素通し）。
`TRUSTED_PROXY_COUNT` の過大設定はフェイルクローズにならず、クライアントが `X-Forwarded-For` に値を詰めて自分の識別子を選べる（`.env.example` 参照）。
守りはデプロイ側の契約——IaC を書く日に replicas=1 を固定するか上流レート制限を必須とし、上流で受信 XFF を上書きする——で、コードでは守れない。デプロイ ADR の必須項目として本 ADR が義務づける。

## 検査

(i) 層 2 — 依存・設定キー・外部送信先（`scripts/adr-touch.sh` が索引行を貼る。`redis` を足す変更は依存の行に当たる）。
(ii) 起動ガード `STARTUP_MULTIPLE_WORKERS`（同一コンテナ内 worker>1 で起動失敗）。外部契約（429 レスポンス・`X-RateLimit-*` / `Retry-After` ヘッダー）は characterization テストで固定してある。
**未検査**: デプロイ側契約と、プロバイダ支出上限。支出上限は backend 公開（AI 変換の有効化）の必須ゲートで、対象プロバイダアカウントにハードリミットを設定し、確認日・上限額・確認手段（管理画面のスクリーンショット等）を本 ADR に書き足してから端末 API キーを配布する（責任者: mozuq。「設定したつもり」と設定済みを機械的に区別するための証跡。台帳 L-58）。
