# ADR-002: レート制限は単一インスタンス前提。memory:// を既定とする

状態: **Draft（レビュー待ち）** ／ 日付: 2026-08-29 ／ 出自: 是正計画 §3 決定2

## 背景と課題

`RATE_LIMIT_STORAGE_URI`（Redis 前提の共有ストア設定）が、8周のレビュー往復のうち
**7周を占めた秘匿機構 `redact_storage_uri`（約184行）の存在理由**だった。独立レビューは
このブランチ最終版にもなお漏えい（netloc の無い URI のクエリ資格情報が素通し）を発見して
おり、「秘密を URI に埋めて第三者ライブラリへ渡す」形は注意深さでは閉じない。

さらに、レート制限が根拠として引用してきた **NFR-101 は「会話内容の端末内保存」の
要件であり、レート制限の要件はどの要件書にも存在しなかった**（独立レビューの発見）。
何を守るのかが決まっていないまま、守り方（共有ストア）だけが先に実装されていた。

## このレート制限が守るもの（要件の定義——本 ADR が正本）

1. **単一送信元（IP）の暴走・burst の抑制**（主目的）: 誤動作クライアントや漏れた
   端末キーの連打が、そのままプロバイダへ流れることを防ぐ
2. 粗い DoS 緩和（副次）

**総費用の上限はレート制限では作れない**（独立レビューの反例: N 個の送信元 IP から
使えば per-IP 制限は総量を縛らない）。総費用の真の上限は **AI プロバイダ側の
支出上限（ハードリミット）**であり、その設定を **backend 公開日の必須条件**とする。
- **非目標**: 利用者間の公平性。想定利用は単一端末で、多数利用者の競合はまだ無い
- 既定値は現行踏襲: 1リクエスト/10秒/IP（`RATE_LIMIT_TIMES` / `RATE_LIMIT_SECONDS`）
- `AGENTS.md` / `api-endpoints.md` の NFR-101 引用は本 ADR への参照に差し替える
  （api-endpoints 分は Phase 5 の正本整理で）

## 検討した選択肢

1. Redis 等の共有ストアで複数インスタンス対応
2. **`memory://`（プロセス内）で単一インスタンス前提**（採用）
3. アプリ内レート制限を持たず、インフラ層（WAF / API Gateway）＋プロバイダ支出上限に任せる
4. レート制限なし

## 決定

案2。`redis` 依存を削除し、`RATE_LIMIT_STORAGE_URI` という設定キー自体を作らない。
`memory://` に秘匿すべき文字は1文字も無いので、秘匿機構ごと不要になる。

## 決定理由（却下した案と理由）

- **案1を却下**: 秘密入り URI が7周の再生産源。利用者ゼロで、必要になる規模に無い。
  **復帰条件**: 実測でマルチインスタンスが必要になり、かつ**資格情報を URI に埋めない
  方式**（ElastiCache IAM 認証等）を採る場合に限る
- **案3は却下ではなく保留**: 今日はインフラが存在せず検証できない。**デプロイ形態の
  ADR で第一候補として再評価**し、採用するならアプリ内カウンタは削除まで戻す
- **案4を却下**: 端末 API キーの漏えいや誤動作クライアントに対して費用が無防備になる

## 守り（計画の ADR 守り表と対応）

- A層: `redis` 依存の削除。足す変更は依存追加ゲートが発火する
- 起動ガード（Phase 2）: 同一コンテナ内 worker>1 ∧ in-memory なら起動失敗。
  **ただし replica は検出できない**（single-worker × 2 replica は素通し）
- **デプロイ側契約**: IaC を書く日に replicas=1 を固定するか、上流レート制限を必須とする。
  これはコードでは守れないため、デプロイ ADR の必須項目として本 ADR が義務づける
- 外部契約（429 レスポンス・`X-RateLimit-*` / `Retry-After` ヘッダー）は
  characterization テストで固定する（Phase 2）
- **プロバイダ支出上限の設定** — backend 公開の必須条件（総費用の上限は
  レート制限ではなくここで作る）

## 再訪条件

デプロイ形態を決める日（案3を第一候補で再評価）。マルチインスタンスが実測で必要に
なった日（復帰条件つきで案1）。
