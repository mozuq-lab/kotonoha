# ADR-005: frontend は1概念1真実。永続化の失敗は利用者に伝える

状態: **承認済み（2026-08-29、署名: mozuq。2系統レビュー反映済み）** ／ 日付: 2026-08-29

## 背景と課題

**お気に入りが4箇所に散っている**: `HistoryItem.isFavorite`（書かれるが常に false、
UI は読まない）／`features/favorite/`（ロジック）／`features/favorites/`（UI）／
`PresetPhrase.isFavorite`（Hive field 3 として**永続化**され、UI が読み、
favoriteNotifier と双方向同期する——独立レビューが検出した4箇所目）。
isFavorite のバグは Hive アダプタのテストが緑のまま生き残った——欠陥は変換層にあり、
テストは層を飛ばして下だけを叩いていた。

**Hive が開けないと黙ってインメモリで動き続ける**: `repository_providers.dart` が
null を返すフォールバックが「意図した設計」として実装されている。発話支援アプリで
「保存できたように見えて消える」は、起動しないことより重い——利用者は発話で確認・
訂正できず、データは端末内にしか無い（B-2 の最悪ケース「データ喪失」）。

## 制約条件

- NFR-301（基本機能継続）: ストレージ障害でも文字盤・TTS は使えるべき（オフラインファースト）
- 利用者は複雑なエラー表示を操作できない。通知は簡潔に

## 検討した選択肢

お気に入りの真実:
1. 現状維持（4箇所併存） 2. `HistoryItem.isFavorite` に一本化
3. **`favoriteProvider` に一本化し、`isFavorite` を Hive migration で削除**（採用）

永続化失敗の扱い:
a. サイレント継続（現状） b. 起動をブロックする
c. **状態を型で明示し、利用者に伝えて継続する**（採用）

## 決定

- お気に入り: 案3。UI が実際に使っている `favoriteProvider` が真実。キーは内容テキスト
  ではなく id にする（同文の定型文で衝突しない）。**migration の対象は
  `HistoryItem.isFavorite` と `PresetPhrase.isFavorite` の両方**で、参照は
  favoriteProvider へ寄せる（片方だけ消すと並行真実が残る）
- 永続化: 案c。`sealed class PersistenceState { Ready / RecoverableFailure / Unavailable }`
  とし、保存されない状態を利用者に通知する（文言・UI は Phase 3 で設計）
- 検査: Hive スキーマ許可リスト（`typeId`・永続フィールド）を CI に置き、
  無断の永続面追加を落とす

## 実装後の補足（2026-08-30 / 31。Phase 3 WP2 の実施で決まったこと）

**この節は決定の変更ではなく、実装して初めて決める必要が出た点の記録である。**
判断はいずれも人が下した。実装は PR #88（main へマージ済み）。

### 1. 真実は1つ。射影は用途ごとに決めてよい

**「キーは id」は `FavoriteItem` のレコード同一性と、定型文連動の同期キー（`sourceId`）に
適用する。UI が利用者に見せる同値関係は用途ごとに決めてよい。**

- **履歴画面の星は content 照合のまま**。sourceId 照合にすると、定型文由来の同文に星が
  付かない／同じ文言を再発話すると付かない／履歴50件上限でアンカーの履歴が消えると
  二度と付かなくなる。上の却下理由が名指しした衝突は「同文の**定型文どうし**」であり、
  それは `addFavoriteFromPresetPhrase` の sourceId 重複判定で解決済み
- **`input_candidate_scorer` はテキスト射影のまま**。`computeCandidates` は `List<String>` しか
  受けず、集計は候補テキストがキー、出力は `InputCandidate(text:, score:)` で、
  **id を持てる場所が型の上に存在しない**。これは並行真実ではなく `favoriteProvider` の射影である

**要点は「真実が `favoriteProvider` に1つであること」であって、
すべての参照を id にすることではない。**

### 2. migration は行わなかった

上の決定は「migration の対象は両方」としているが、**移行は実装してレビューまで通したうえで
撤回した**（`f761afc`）。守る価値のあるデータが検証端末に無いという判断による。
残していた場合、(1) お気に入り画面から削除したものが再起動で復活する（UI から到達可能）
(2) 移行は `PresetPhrase.isFavorite` を読むので、そのフィールドを消すビルドと共存できない、
の2つが避けられなかった。**フィールドは両方とも削除済みで、並行真実は消えている。**

### 3. 未解決: 却下理由と実装が矛盾している（台帳 L-39）

上の「お気に入り案2を却下」の決め手は「お気に入りは**項目の削除・保持上限と独立に
生きるべきもの**」だが、`deletePhrase()` は `deleteFavoriteBySourceId()` を呼び、
定型文を消すとお気に入りも消える。`TC-SYNC-202`（要件定義3.2「孤立データ防止」由来）が
**それを正解として固定している**ため、**全テスト緑はこの不適合を反証しない。**

2026-08-30 の対応は「振る舞いは変えず、削除確認ダイアログに『お気に入りからも削除されます』を
出す」（登録済みのときだけ）。**矛盾そのものは未解決で、解くには本 ADR か要件定義3.2 の
改訂が要る。**

### 4. 検査（許可リスト）が何を守り、何を守らないか（2026-08-31 / Phase 3 WP-5）

上の決定は「Hive スキーマ許可リスト（`typeId`・永続フィールド）を CI に置き、
無断の永続面追加を落とす」とだけ書いている。**実装して初めて決める必要が出た点**を
記録する。実装は `test/core/persistence/hive_schema_allowlist_test.dart`。

**守る経路は「起動時の共有登録経路」**。検査は `initHive()` が呼ぶのと同じ
`registerPersistedTypeAdapters()` を呼び、**その関数が登録した実体だけ**を見る。
検査側が一覧を書き写すと、本番にだけ足された永続化面を見逃す（台帳 L-31）。

**守らないもの（構造でも権威でも塞げないので、記録して受け入れた）**:
共有関数を経由しない直接の `Hive.registerAdapter` / `Hive.openBox`。
Dart には「この API を他所で呼ばせない」構造が無く、開かれている box を列挙する
公開 API も Hive に無い。**自作の検出器は作らない**
（`verification-principles.md`「P1 の処方箋」／ADR-008）。受け皿は
`AGENTS.md`「負債を作る行為には理由が要る」節と、層1・層3・層5。

**検査自身が穴を作りうることが分かった。** 当初の実装は「typeId が増えたら赤」に
なるが、赤いメッセージが「許可リストを更新せよ」と指示するため、指示どおり
typeId を足すと**そのアダプタのフィールド番号・型は以後どの検査も見ない**状態で
緑に戻った（2026-08-31 の2系統レビューで指摘）。検査を足すのではなく、
登録の観測点を1つにする**構造の変更**で塞いだ。

**「トップレベル可変変数の禁止」は analyzer では実現できない。**
是正計画は analyzer ルールとして挙げていたが、`avoid_top_level_mutable_variables`
も `avoid_global_state` も Dart に存在しない（`undefined_lint`。2026-08-31 実測）。
これも記録して受け入れた。代わりに、守る対象が文書に名指しされている4つの lint を
入れ、**CI で実際に落ちる強さ（warning）まで昇格**してある——lint の既定の info は
`flutter analyze --no-fatal-infos` を通過するため、入れても一度も発火しない。

### 5. 往復テストで層を飛ばさない（2026-08-31 / Phase 3 WP-3）

「1概念1真実」は、真実が1つであることを**最も外側の境界**で確かめないと守られない。
`isFavorite` のバグは Hive アダプタのテストが緑のまま生き残り、バグはその上の
変換層にあった。UI → provider → repository → 実 box → 再起動相当 → UI を通す
往復テストを4 feature（history / preset_phrase / favorite / settings）に置いた。
定型文の往復は presetPhrases box と favorites box の**2つをまたぐ**ので、
定型文側にフラグが残っていたら通らない。

## 決定理由（却下した案と理由）

- **お気に入り案1を却下**: 多重実装の温存。「タグ機能を追加して」の日に5つ目が生まれる
- **お気に入り案2を却下**: 決め手は**概念の所有者とライフサイクル**——お気に入りは
  「項目に付くフラグ」ではなく「履歴・定型文をまたいで参照する独立のコレクション」で、
  項目の削除・保持上限と独立に生きるべきもの。フラグ方式は項目の寿命にお気に入りの
  寿命を結合してしまう。（当初の却下理由「UI が読んでいない・往復テストが無い」は
  現状の欠陥であって案の本質的欠陥ではない、という独立レビューの指摘を受けて書き直した。
  UI 更新とテスト追加を同条件で仮定しても、所有者の理由で案3が優る）
- **永続化案aを却下**: データ喪失を利用者が知る手段が無い
- **永続化案bを却下**: NFR-301 に反する。インメモリでも話せる方がよい——ただし
  **保存されないことは必ず伝える**

## 限界（正直な穴）

永続フィールドを伴わない「UI ロジックだけの重複」は許可リストで捕まえられない
（favorite/favorites がまさにその形だった）。月1の棚卸し（Phase 4）で拾う。

## 再訪条件

利用者・支援者からの実フィードバックで通知の形が使えないと分かったとき。
**判定手段**（独立レビューの指摘——非クラッシュ不具合はクラッシュ報告に映らない）:
月1の巡回（Phase 4 の棚卸しと同周期）で、ストアレビューとサポート窓口への報告を
確認する。受付経路はストア掲載のサポート連絡先（ADR-007）。
