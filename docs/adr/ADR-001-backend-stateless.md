# ADR-001: backend はステートレス。サーバー側にユーザー状態を持たない

状態: **承認済み（2026-08-29、署名: mozuq。2系統レビュー反映済み）** ／ 日付: 2026-08-29 ／ 出自: 是正計画 §3 決定1

## 背景と課題

backend の DB（PostgreSQL + SQLAlchemy + alembic）は**書き込み専用**である。実測:
`app/db/` の外に**テーブルを読む** SELECT は0件（接続確認の `SELECT 1` が
health check 2箇所にあるのみ）、`crud/` の関数は `create_conversion_log` 1つ、
`ai_conversion_logs` / `error_logs` を読む処理はどこにも無い。ER 図自身が
「AI変換ログとエラーログは将来的な拡張と統計用であり、MVP範囲で必須ではない」と
明記している（`docs/design/kotonoha/database-erd.md`）。

この DB が生んだ実害:

- `%` / `@` を含むパスワードで接続できないバグ（418テスト緑のまま生存）
- alembic が DSN 全文を例外に載せる漏えい
- `core → db → core` のパッケージ循環（8周のレビューが一度も検出せず）
- `error_message=str(error)` という「一度書いたら消えないシンク」
- **プライバシーポリシー違反**: 入力のソルト無し SHA-256・文字数・セッション UUID の
  サーバー保存は、NFR-101「会話内容は端末内にのみ保存」に反する。文字盤由来の短い
  発話はハッシュから辞書探索で復元しうる（input_length まで保存していた）

## 制約条件

- NFR-101: 利用者の会話内容は端末内にのみ保存しなければならない
- 運用情報（レイテンシ・成功率・プロバイダ別エラー率）は捨てない
- 本番デプロイ・リリースは一度も行われておらず、移行すべき実データが無い

## 検討した選択肢

1. DB を維持し、読む機能（統計画面等）を後付けする
2. DB を現状のまま維持する
3. **DB を外してステートレスにし、運用情報は stdout 構造化ログ（JSON）で取る**（採用）
4. DB の代わりに外部テレメトリ基盤（OpenTelemetry / CloudWatch EMF）を今導入する

## 決定

案3。`app/models` `app/crud` `app/db` `alembic` と、依存5行
（`sqlalchemy` `alembic` `asyncpg` `psycopg2-binary` `redis`）を削除する（Phase 2）。
構造化ログには**ユーザー由来の内容を一切載せない**——ハッシュも文字数も載せない。

## 決定理由（却下した案と理由）

- **案1を却下**: 読む要件がどの要件書にも存在しない。要件が生まれた日に、依存追加
  ゲートに止められた時点で新しい ADR から始めれば足りる
- **案2を却下**: 読み手ゼロのまま本番コード1,135行・秘密1種（`POSTGRES_PASSWORD`）・
  VPC/RDS のデプロイ複雑性を維持する理由が無い。NFR-101 違反も続く
- **案4を却下**: 集約基盤が無い今日に入れても検証できない。stdout JSON はどの集約基盤
  にもそのまま乗るので、デプロイ形態が決まる日の ADR で再訪すれば十分

## 影響

- 本番コード 1,135行（`app/` 内 521 + alembic 系 614）とテスト約1,700行が消える
- 秘密は `API_KEYS` と AI プロバイダキーの2種類に減り、どちらもプロセス内で完結する
- docker-compose / CI から postgres が消える。恒常失敗していた migration テスト2本も消える
- privacy-policy.md が実装と自動的に整合する（Phase 5 で文言を更新）

## 再訪条件

サーバー側に状態を要する機能要求が実際に出たとき（依存追加ゲートが強制的にここへ戻す）。
ログの集約・保持期間・検索・アラートはデプロイ形態の ADR（未起草）で決める。
