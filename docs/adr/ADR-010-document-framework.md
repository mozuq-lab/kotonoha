# ADR-010: 文書と判断の枠組み — エージェントが判断し、人は外への影響と製品の約束だけを決める

状態: 承認済み（2026-09-05 決定、2026-09-12 改訂、2026-09-24 書き直し: 文書の枠組みに判断の手順を加えた。署名: mozuq）／ 出自: 2026-09-23〜24 の 2 回のパネル（前提の検証と、LLM の力を引き出す仕組み）

## 背景と課題

2026-08〜09 の 3 つの出来事は同じ形だった。秘匿関数の修正とレビューが 8 周しても収束しなかった。ADR と規則は失敗のたびに増え、上限を置いてもほかの置き場へ移った。下書きの小修正の PR は、4 系統レビューの指摘に応えるうちに 397 行から 605 行へ伸び、台帳は 3 日で 41 行増えた。
仕事の単位が「最新の指摘に局所的に正しく応えること」で、応え方がいつも足し算だった。どの一歩も正しいので、止まる理由が作業の中に無かった。人の個人開発者なら、疲労と費用が止めてくれる。
パネルは、見落としていた原因も挙げた。仕事の出所がエージェント自身だったこと（推測で足した要件、レビューの指摘）、何に取り組むかを決める所が無かったこと、規則そのものが重い手続きを要求していたこと、人の承認が形だけになっていたこと。
止め具を「エージェントの判断」に置いた仕組み（「3 周したら問い直す」フック、差分を ADR に当てる自作ツール、規律 7 の基準）は、3 回とも発火しなかった。

## 制約

- 人は固定の予算を置かない。レビューを縛らない。介入するのは本当に必要な所だけにする
- 止める機械を作らない（倉庫の ADR-008）。数字は数えるだけにする
- 1 人＋エージェントの体制。参照の費用が利点を上回る仕組みは持たない

## 検討した選択肢

1. 失敗のたびに規則・検査・記録を足す（2026-08〜09 の実績）
2. 固定の予算・周回の上限・人の事前承認で止める
3. **何をするかを上書きの 1 枚（`docs/now.md`）で決め、判断はエージェントが手順に沿って行い、人は外への影響と製品の約束だけを決める。止め具はエージェントが言い換えられない事実（パス・git・実物の録画）に置く**（採用）
4. 裁定役・削除役など、別のエージェントを常設する

## 決定

文書は 6 種類。核 `AGENTS.md`（毎回読む。規則を 1 つ足すなら 1 つ消す）／現在地 `docs/now.md`（目的・「形」の定義・最短経路・人待ち。上書きし、日誌にしない）／決定 `docs/adr/`（製品の約束と、却下した案の記録だけ。各 60 行・未卒業 5 本。検査で守れる決定は検査と同じ PR で入れ、卒業済みとして生まれる）／正本（読者ごとに 1 つ）／使い捨て（`docs/plans/` と PR 本文）／倉庫 `docs/archive/`。
判断の手順は AGENTS.md に置く。仕事の入口は最短経路と人の依頼だけで、動かせるものが無ければ止まる。等級はパスで最低等級が決まり、エージェントは上げるだけ。検証の重さは等級で決まる。指摘は既定で捨て、直す側が証拠を出す。同じ関数を 2 回変えたら、次の一手を設計・削る・閉じるから選ぶ。人が決めるのは、外への影響・製品の約束・取り返しのつかないデータ移行。それ以外はエージェントが決め、PR に書き、人は事後に覆す。
ADR は、A 級に着手するときと決定を変えるときに、「却下した案」の列と照らす。PR ごとの yes/no 表は作らない。レビュー指摘に応えて ADR に文を足さない。決定が変わったら、追記せずに書き直す。
台帳 `docs/ledger.md` には、決めた予定（`[ ]`）と、利用者に見える受け入れた限界（`[~]`）だけを置く。直さない指摘は記録しない。`[x]` と `[-]` は、付けた PR で行ごと消す（履歴は git）。
PR 本文の、人に読ませる部分は 1 画面に収める（何が変わるか／判断をお願いしたいこと／私が決めたこと／確かめたこと・確かめていないこと）。記録は `<details>` に入れる。
監査は、ストア提出の前・人が頼んだとき・保存送信の経路を変えるときに行う。見るものは 2 つ。正しさは、コードから公開文へのデータの流れを追う。増え方は、全置き場（AGENTS.md・ADR・台帳・スキル・メモリ・作業場）の文字数を数え、不要になった仕事と消すものを挙げる。消すのはエージェントが行う。

## 決定理由と却下案

- 案 1 却下: 足した規則は発火せず、上限を置いても別の置き場へ伸びた（行数の上限は 1 行を長くしてすり抜けた）
- 案 2 却下: 人の前提（予算を置かない、介入は最小）に反する。周回の上限は、形を変えた予算になる
- 案 4 却下: 同じ盲点を持つ層が 1 つ増えるだけ。常設の自作の仕組みは、Stop フックと同じく発火しなくなる
- 月 1 の定期棚卸し 却下: リリース後は月単位で触らないことがあり、変わっていないものを監査しても何も出ない
- 全部を記録する台帳 却下: 記録が次の仕事の入口になった。「受け入れた限界」も作業中に 11 行から 24 行へ伸びた

## 限界

等級のパスの一覧は、それ自体が伸びうる。監査で数える。
「同じ関数を 2 回」は、隣の関数を変えれば避けられるので、強制ではなく合図として扱う。
仕分けは最終的にエージェントの判断で、指摘に従う方向の偏りは残る。受け皿は、人の事後の覆しと監査。
物理実機での確認はストア提出の前まで無い。シミュレータとエミュレータで観測できるのは、挙動と見た目だけ。

## 検査

無し。監査で、全置き場の文字数と「不要になった仕事」の列挙を見る（`scripts/inventory.sh` は数えるだけ）。

## 再訪条件

1 つの PR が、この手順の下でも 2 回続けて大きく膨らんだとき（手順が効いていない）。人が事後に覆した決定が続いたとき（等級か仕分けの基準がずれている）。監査のたびに総量が増えているとき。
