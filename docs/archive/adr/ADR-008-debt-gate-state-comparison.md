# ADR-008: 負債ゲートを機械では作らない（状態比較案を却下）

状態: **却下（2026-08-30、署名: 未署名）** ／ 日付: 2026-08-29 起案・2026-08-30 却下

> **ファイル名は起案時の案（状態比較）のまま**にしてある。台帳 Issue #85 のコメントが
> このパスを参照しているため。**決定は「機械のゲートを作らない」である。**

## この ADR を読む人へ

**負債ゲート（依存追加・権限追加などを CI で検出して ADR 引用を要求する仕組み）を
作ろうとして、3周かけて失敗した記録である。** 同じものを作り直そうとしているなら、
まず「引き継ぐ教訓」を読むこと。**前提は正しかったが、作り方が3周とも同じ誤りだった。**

> **この失敗は負債ゲートに固有ではない。** 2026-08-30 の Phase 3 WP-1 で、
> レビュー指摘に応えて grep ベースの不変条件検査を作り、**同じ形で3周を費やした**
> （権威＝Dart のパーサを文字列照合で再実装した）。この ADR を読んだうえでの再演である。
>
> **文書は発火しない。** そこで教訓は ADR を増やす形ではなく、実際にレビューの入力と
> なる `docs/verification-principles.md` の**トリアージ規約そのもの**へ移した。
> 「P1 の処方箋 — 検査を自作する前に、構造を変えられないか問う」を参照すること。
> **検査を新しく作ろうとしているなら、この ADR より先にそちらを読むこと。**

## 背景と課題

是正計画 §5 は、ADR を守らせる仕組みを3層に分けた。

| 層 | やり方 |
|---|---|
| A. 消す | 選択肢そのものを無くす（依存を消す、受け取る型を作らない） |
| B. 押し出す | `AGENTS.md` に決定の1行要約を置く |
| **C. ゲートを張る** | 「負債を作る**行為**」を CI で検出し、ADR の引用を要求する |

C の根拠は「**決定は無限に増えるが、負債を作る行為は有限である**」——事前に全決定を
書かなくても「決定が要る場面」は検出できる、という主張だった。

## 前提は正しかった（実測）

**却下する前に、前提の成否を確かめた。** 8周を引き起こした2つの原因が実際に入った経路は:

```
sqlalchemy               2025-11-20  backend/requirements.txt から
RATE_LIMIT_STORAGE_URI   2026-07-20  backend/.env.example から
```

どちらもゲートが見ていた面であり、**許可リストから外して当てると両方とも検出できた**
（exit=1、2026-08-30 実測）。**「決定が要る場面を機械が検出する」という発想自体は
外れていない。** 却下の理由は前提ではなく、実装の収束しなさである。

## 検討した選択肢

1. **差分のパターン照合**（正規表現＋AST で「負債を作るコードの書き方」を検出）
2. **ゲートを作らず、層1（着手前の影響範囲）・層3（差分レビュー）・層5（棚卸し）に任せる**
3. **状態比較**（正規パーサで状態を読み、集合にして許可リストと比べる）
4. 全項目を AST・構文解析まで上げる

起案時は案3を採用した。**3周の実装と6回の独立レビューを経て、案2へ切り替える。**

## 決定

**案2。負債ゲートを機械では作らない。**

- `scripts/debt_gate/` と `.debt-gate/` を削除する
- ゲートの CI ジョブを削除する
- 受け皿は `AGENTS.md` の「機械が見ていない負債」節（人の規律）＋
  層1（着手前の影響範囲）＋層3（差分レビュー）＋層5（月1の棚卸し）
- `openspec/changes/` の tracked ファイル禁止は**残す**。ゲートとは設計上無関係で、
  `git ls-files` 3行で完結し、是正計画 §5 条件1 という別の要件に由来する

## 決定理由

### 3周とも収束しなかった

| | 1周目 | 2周目 | 3周目 |
|---|---|---|---|
| 方式 | 差分のパターン照合 | 状態比較（許可リスト） | 同左＋7件の修正 |
| 独立レビューの指摘 | 約20件 | 約15件 | 17件 / 6件（2系統で判定が割れた） |
| 変更行数 | 1,939 | 1,585 | 1,134 |
| mutation kill rate | — | 60% / 20% | 81% / 80% |

**計画が定めた1周の上限は 400行 / 12ファイル（§5「OpenSpec を使う条件」）。3周とも
超えている。** 計画は「1つの change を大きくすると『1周10〜15件をまとめて直す』が
再演される」と、この失敗を予告していた。

### 単一の根本原因: 他人が持つ権威を再実装した

3周の指摘の分布が、原因をはっきり示している。

| 検査 | 権威 | 実装 | 3周での指摘 |
|---|---|---|---|
| Android 権限 | XML パーサ | **権威をそのまま使った** | **0件** |
| iOS 権限キー | plist パーサ | **権威をそのまま使った** | **0件** |
| Python 依存 | pip（requirements 文法の所有者） | pip の文法を**再実装** | 3周とも |
| 設定キー | python-dotenv | dotenv の文法を**再実装** | 3周とも |
| Dart 依存 | Dart の resolver（`pubspec.lock` がその出力） | `pubspec.yaml` を自前解釈 | 供給元 URL を見逃す |

**権威をそのまま使った2つは指摘ゼロ、再実装した3つは毎周指摘あり。** 偶然の分布ではない。

これは `docs/verification-principles.md` が既に記録していた教訓
（「ライブラリが持つ集合を参照しておきながら手書きで足さない」）の一般形であり、
**8周のとき `limits.SCHEMES` に `| {"unix"}` を手書きで足したのと同じ誤りを3回繰り返した。**

### 「安全な検査だけ残す」が成立しない

3周目の指摘の多くは検出器ではなく**枠組み側**にあった——ディレクトリ改名で許可リスト
78行の手編集、`grandfathered` の手書きによる素通し、`seed` の再実行、`MINIMUM_TESTS` が
テスト9本の削除を見逃す、識別子にパスを含めた副作用。指摘ゼロの2検査だけ残しても、
**枠組み 2,054行はそのまま残り、そこに3周目の欠陥の多くがあった。**

### 発火実績がゼロ

- 許可リスト95件は**すべて経過措置**（`grandfathered`）。**ADR 引用の分岐は一度も
  実行されていない**
- **CI で一度も動いていない**（7コミット未 push。`workflow not found on the default branch`）
- 「決定が要る場面」の実測頻度は**年に数回**（sqlalchemy 2025-11、`RATE_LIMIT_STORAGE_URI` 2026-07）

**年数回の事象のために、CI ジョブと 2,054行と3周のレビューを払った。** 割に合わない。

### 運用上の実害が残っていた

削除時点で再現できていた偽陽性:

- `pip-compile --generate-hashes` の標準形で CI が止まる
- `python-jose` → `python_jose`（pip では同一）で stale と unlisted の2箇所が落ちる
- `.env` の複数行の値・値なしキー（dotenv の有効表記）で止まる
- ディレクトリの改名で許可リスト78行の手編集

ADR-008 起案時に自分で書いた撤回条件——「**ブロックする検査の偽陽性で開発が止まった →
その項目を助言へ降格する**」——が、実際に発火した。

## 却下した案と、その理由

- **案1（差分のパターン照合）**: 1周目に実装し revert した。有効な別の書き方が
  7項目中6項目に存在した（4スペース indent の依存追加・タグ改行した plist キー・
  大文字名の資源生成・`for` ループ内の副作用・`add_route`）。**入力空間が無限なので、
  1つずつ塞ぐのは8周と同じ「事例の列挙」になる**
- **案3（状態比較）**: 2〜3周目に実装した。フォーマットの内側では確かに閉じたが、
  **どの権威を消費し、identity に何を含めるかを、レビューのたびに足す設計**になり
  収束しなかった（上記）
- **案4（全項目を AST へ）**: 整形には閉じるが意味には閉じない。実測で `for` ループ・
  デコレータ・反転 main guard・大文字名が素通しした

## 引き継ぐ教訓（再挑戦するなら、まずこれを満たすこと）

1. **検査は権威の出力を消費する。権威を再実装しない。**
   消費できる出力が無い面は、機械で検査しない（人の規律に置く）。
   - Dart 依存 → `pubspec.lock`（resolver の出力）。`pubspec.yaml` を自前解釈しない
   - Python 依存 → lock か hash 固定のファイル。pip の行文法を書かない
   - 設定キー → python-dotenv を**ライブラリとして呼ぶ**
   - 公開ルート → `app.openapi()` を実行する。**identity は `(パス, メソッド)`**
     （パスだけだと既存パスに `POST` を足す変更が素通しする）
   - Hive スキーマ → **Dart 側に typeId と永続フィールドを吐くテストを置き、その出力を読む。**
     手書きアダプタを Python の regex で読むと、案1へ逆戻りする
   - `ios/Podfile`・`android/**/build.gradle.kts` → 消費できる出力が無い。**検査しない**
2. **1周は 400行 / 12ファイルまで。** 超えたらスコープを割る。3周ともこれを破った
3. **枠組みを持たない。** 許可リスト・経過措置・seed・identity 設計を持つと、
   検出器より枠組みの欠陥のほうが多くなる
4. **発火実績で測る。** 「検査が存在する」ではなく「実際に決定を要求した回数」で
   価値を判定する。ゼロのまま3周続けたのが今回の失敗

## 影響

### 失うもの

- 依存追加・モバイル権限追加・設定キー追加の**機械的な検出**。8周の原因2つは
  この面から入っており、機械では止まらなくなる
- 層2（機械）が差分の外を見る手段は、既存の `import-linter` / `mypy --strict`
  （Phase 2 で導入予定）に限られる

### 残すもの

- `AGENTS.md`「機械が見ていない負債」節——**削除後はここが唯一の受け皿になる**
- `openspec/changes/` の tracked ファイル禁止（独立した CI ジョブ）
- 本 ADR（この記録自体）

### この決定を見直す条件

- **決定が要る場面の頻度が上がったとき**（年数回 → 月1以上）。いまは頻度が低すぎて
  機械化が割に合わない
- **権威の出力をそのまま消費できる面が3つ以上そろったとき**（`pubspec.lock`＋
  OpenAPI＋Hive スキーマのテスト出力）。その場合も上の教訓1〜4を先に満たすこと

## 置き換える ADR

なし。ADR-001〜007 は変更しない。本 ADR はそれらを**守る仕組み**についての決定であり、
決定そのものは変わらない。
