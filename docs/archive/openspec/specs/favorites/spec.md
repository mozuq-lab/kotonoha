# お気に入り（favorites）

> **これは実装済みの振る舞いの baseline 書き取りである**（是正計画 §5 条件2）。
> propose → apply の対象ではない。根拠は ADR-005（補足を含む）と Phase 3 WP-2 の実装。

## Purpose

お気に入りは「項目に付くフラグ」ではなく、**履歴・定型文をまたいで参照する独立の
コレクション**である。真実を1つ（`favoriteProvider`）に保ち、項目の削除や保持上限と
独立に生きられるようにする。

## Requirements

### Requirement: お気に入りの真実は1つ

システムはお気に入りの状態を `favoriteProvider` にのみ SHALL 保持する。
履歴・定型文のモデルにお気に入りを表すフィールドを持ってはならない
（並行真実になるため。ADR-005「1概念1真実」）。

**射影は用途ごとに決めてよい。** 要点は真実が1つであることであって、
すべての参照を id で行うことではない。

#### Scenario: 定型文の一覧はお気に入りの真実から描かれる
- **WHEN** 定型文の一覧を表示する
- **THEN** 各定型文がお気に入りかどうかは `favoriteProvider` の内容から決まる
- **AND** 定型文のモデル自身はお気に入りかどうかを保持しない

#### Scenario: 履歴の一覧はお気に入りの真実から描かれる
- **WHEN** 履歴の一覧を表示する
- **THEN** 各履歴がお気に入りかどうかは `favoriteProvider` の内容から決まる
- **AND** 履歴のモデル自身はお気に入りかどうかを保持しない

### Requirement: 同じ文言のお気に入りを重ねて作らない

システムは、内容が同じお気に入りを重複して SHALL 作らない。
履歴由来の登録も内容一致で判定する——利用者は同じ文言を何度も発話するので、
出所の id で判定すると発話のたびにお気に入りが増えて一覧が同じ文言で埋まる。

#### Scenario: 同じ内容を二度お気に入りにする
- **WHEN** すでにお気に入りにある内容を、もう一度お気に入りにしようとする
- **THEN** 新しいお気に入りは作られない

#### Scenario: 同じ文言を再度発話してから履歴からお気に入りにする
- **WHEN** 同じ文言の履歴が複数あり、そのうち1つをお気に入りにしている
- **THEN** 別の履歴から同じ文言をお気に入りにしても増えない

#### Scenario: 空文字はお気に入りにしない
- **WHEN** 空の内容をお気に入りにしようとする
- **THEN** 何も作られない

### Requirement: 定型文由来のお気に入りは出所の id で同一性を判定する

システムは定型文から作られたお気に入りについて、**出所の定型文 id** で重複を
SHALL 判定する。同じ文言の定型文が2つあっても、それぞれ別のお気に入りとして
登録・解除できなければならない。

#### Scenario: 同じ文言の定型文が2つある
- **WHEN** 内容が同じ定型文 A と B があり、A をお気に入りにしている
- **THEN** B もお気に入りにできる

#### Scenario: 同じ定型文を二度お気に入りにする
- **WHEN** すでにお気に入りの定型文を、もう一度お気に入りにしようとする
- **THEN** 新しいお気に入りは作られない

### Requirement: お気に入りは出所を記録する

システムはお気に入りが履歴由来か定型文由来かと、その出所の id を SHALL 記録する。
出所は定型文との連動に使う。履歴由来の出所は記録のみで、重複判定には使わない。

#### Scenario: 履歴から登録する
- **WHEN** 履歴からお気に入りに登録する
- **THEN** 出所の種類は履歴、出所 id はその履歴の id になる

#### Scenario: 定型文から登録する
- **WHEN** 定型文からお気に入りに登録する
- **THEN** 出所の種類は定型文、出所 id はその定型文の id になる

### Requirement: 定型文を削除すると、その定型文由来のお気に入りも削除される

システムは定型文が削除されたとき、その定型文を出所とするお気に入りを
SHALL 削除する（要件定義3.2「孤立データ防止」）。削除の確認ダイアログでは、
お気に入りからも消えることを利用者に伝えなければならない。

> **既知の不整合（台帳 L-39）**: この振る舞いは ADR-005 が案2を却下した決め手
> 「お気に入りは項目の削除・保持上限と独立に生きるべきもの」と食い違っている。
> **テストが緑であることはこの不整合を反証しない**（`TC-SYNC-202` がこの振る舞いを
> 正解として固定しているため）。解くには ADR-005 か要件定義3.2 の改訂が要る。
> ここには**実装されている振る舞い**を書いてある。

#### Scenario: お気に入り登録済みの定型文を削除する
- **WHEN** お気に入りに登録済みの定型文を削除する
- **THEN** 対応するお気に入りも削除される
- **AND** 削除の確認時に、お気に入りからも消えることが利用者に示される

#### Scenario: お気に入りでない定型文を削除する
- **WHEN** お気に入りに登録していない定型文を削除する
- **THEN** お気に入りは変化しない

### Requirement: お気に入りの削除は取り消せる

システムはお気に入りの削除（1件・全件のいずれも）を SHALL 取り消せるようにする。
利用者は発話で訂正できないため、誤操作からの復帰手段が要る。

#### Scenario: 1件削除してすぐ取り消す
- **WHEN** お気に入りを1件削除した直後に取り消す
- **THEN** 削除したお気に入りが元の内容で戻る

#### Scenario: 全件削除してすぐ取り消す
- **WHEN** お気に入りを全件削除した直後に取り消す
- **THEN** 削除したお気に入りがすべて戻る

### Requirement: お気に入りは端末内に永続化され、失敗は利用者に伝わる

システムはお気に入りを端末内（Hive）に SHALL 永続化する。
永続化が利用できない場合でもお気に入りの操作自体は継続できなければならないが、
**保存されていないことは利用者に伝えなければならない**
（`persistence-state` の「保存できないことを利用者に伝える」を参照）。

#### Scenario: 保存できない状態でお気に入りを操作する
- **WHEN** お気に入りの領域が保存できない状態でお気に入りを追加する
- **THEN** 画面上はお気に入りに追加される
- **AND** 保存できないことがバナーで示される
