## 1. この計画が生まれた理由

「設定値の秘密情報がログ・例外・DB に漏れる」問題で、修正 → AI レビュー → 再指摘を
**8周**繰り返したが収束しなかった。うち1周は前周の修正が作った穴だった。

原因を2系統（Claude / Codex CLI）で独立に調べた結果、**複合要因**だった。コードの欠陥は
実在し（独立レビューがブランチ最終版にも「netloc の無い URI のクエリに資格情報が素通し」の
漏えいを発見した）、レート制限が引用する要件 ID も誤っていた（NFR-101 は端末内保存の要件で、
レート制限の要件は要件書に存在しない）。そのうえで**最大の単一要因は、決めていなかった
2つの設計判断**である——`RATE_LIMIT_STORAGE_URI` が無ければ秘匿関数も8周のうち7周も
存在せず、書き込み専用 DB が無ければ残り1周も無い。

このプロジェクトは 2025-10 に Claude 4 + Tsumiki で開始し、技術選定はしたが
**アーキテクチャを詰めていない**。全体方針に沿うことはあまり意識されず、
その時々の判断で実装されてきた。8周はその帰結である。

**インフラのデプロイもアプリのリリースも、まだ一度も行われていない。**
移行すべき実データが無いため、大きな構造変更のコストが例外的に低い。

## 3. 決定

### 決定1 — backend からデータベースを外す

**実測**: `app/db/` の外に**テーブルを読む** SELECT が **0件**（接続確認の `SELECT 1` が
health check 2箇所のみ）。`crud/` の関数は
`create_conversion_log` ただ1つ。`ai_conversion_logs` と `error_logs` は
**書き込み専用**で、何も読まない。

この DB が次のすべての原因である。

| 消えるもの | 内訳 |
|---|---|
| `%` / `@` を含むパスワードで DB に接続できないバグ | DSN が無くなる |
| alembic が DSN 全文を例外に載せる漏えい | alembic が無くなる |
| `core → db → core` のパッケージ循環 | `core/exceptions.py` が db を import するのは `error_logs` に書くためだけ |
| 「消えないシンク」 | `error_message=str(error)` の行き先が無くなる |
| プライバシーポリシー違反 | 入力のソルト無し SHA-256・文字数・セッションUUID の保存が無くなる |
| 恒常的に失敗している migration テスト2本 | |
| 本番コード **1,135行**（`app/` 内 521行＝14.7%。alembic 系 614行を含めた本番コード 4,159行の 27.3%） | `db/` 183 + `models/` 254 + `crud/` 84 + `alembic/` 465 + `alembic.ini` 149 |
| 削除できるテスト 約1,700行 | `test_models_logs.py` 963 / `db/test_session.py` 341 ほか |
| docker-compose と CI の postgres、conftest の DB fixture 群 | |
| デプロイの複雑さ | VPC・RDS・DBパスワードのローテーションが不要。ステートレスなコンテナ1つになる |

**運用情報は捨てない。** レイテンシ・成功率・プロバイダ別エラー率は標準出力への
構造化ログ（JSON）で取る。**ユーザー由来の内容を一切含めない**——入力のハッシュも
文字数も要らない。ログに何が載るか（latency・成否・プロバイダ）は Phase 2 のテストで
観測して固定する。集約・保持期間・検索・アラートは**デプロイ形態が決まる日の ADR で
決める**——基盤が無い今日に決めても検証できない。

将来サーバー側の状態が要る機能が出たら、そのときステートレスなサービスに DB を足す。
逆（後から外す）が難しいことは、この4日間が証明した。

### 決定2 — レート制限を単一インスタンス前提にする

8周のうち**7周を占めた `redact_storage_uri`**（秘匿機構 約184行）は、Redis 接続URIの
パスワードを伏せるためだけの関数である。`memory://` には秘匿すべきものが
1文字もないので、関数ごと不要になる。

**この関数は `main` には存在しない**（`fix/backend-production-hardening` 上のみ。
main の `rate_limit.py` は198行で、秘匿処理を持たない）。つまり決定2は、
「既にあるものを消す」のではなく **「作りかけのものを引き取らない」** 判断である。

利用者ゼロ・単一端末完結・backend は AI 変換のみ。マルチワーカーが必要になる規模には
当分到達しない。必要になった日に、そのとき数値を見て Redis を足す。

この前提が現実に破れる経路は「redis を足す」（依存ゲートが発火する）ではなく、
**「`memory://` のまま worker / replica を増やす」**である——リポジトリ外の変更で、
症状は制限が実効 N 倍に緩むだけのサイレント。だから守りは依存だけでなく
プロセス数にも張る（Phase 2 の起動ガード）。ただし起動ガードが検出できるのは
**同一コンテナ内の worker 数まで**で、single-worker のコンテナを 2 replica にすれば
両方ともガードを通る（独立レビューの反例）。replica 数はアプリから観測できないので、
**デプロイ側の契約として ADR-002 に義務を書く**: IaC を書く日に replicas=1 を固定するか、
上流のレート制限（WAF / API Gateway）を必須とする。

足す日の条件も ADR-002 に今書いておく: **資格情報を URI に埋めない方式**（IAM 認証等）に
限る（8周の問題が同じ形で戻る経路を塞ぐ）。代替として、デプロイ時にインフラ層の
スロットリング（WAF / API Gateway）＋プロバイダ側の支出上限で**アプリ内カウンタ自体を
不要にする**選択肢も、却下案欄に検討跡として残す。

### この2つで、8周が対象にしていたものが全部消える

| 8周で扱った問題 | 原因の秘密 | 決定後 |
|---|---|---|
| 秘匿7周（`redact_storage_uri`） | `RATE_LIMIT_STORAGE_URI` | 決定2で消滅 |
| `%`/`@` 接続バグ・alembic 漏えい・DBシンク | `POSTGRES_PASSWORD` | 決定1で消滅 |
| 端末APIキー認証 | `API_KEYS` | 残る |
| AI プロバイダ呼び出し | `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` | 残る — **サーバーが存在する唯一の理由** |

秘密は5つから2種類に減り、どちらもプロセス内で完結する。
秘匿は「漏らさないよう注意する」ではなく「渡す先が無い」になる。

## 4. backend と frontend は逆の扱いにする

| | backend | frontend |
|---|---|---|
| 規模 | 3,545行 / 公開ルート5本 / ドメインなし | 19,358行 / 8画面 / 17 feature |
| 正体 | ステートレスな AI 変換プロキシ | **プロダクトそのもの** |
| 存在理由 | AI プロバイダのキーを端末に置けない、それだけ | 利用者が触れるすべて |
| 方針 | **書き直す**（到達点 約1,000行） | **直す** |

**backend を書き直す理由**: 決定1・2で 1,135行が消え、`config.py` の半分と
`rate_limit.py` の184行も消える。残すのは `ai_client.py` のプロバイダ処理と
プロンプト、`schemas/` の入出力定義だけ。**リファクタリングより書き直しのほうが小さい。**
既存を段階的に直すと、消える予定のコードにテストを書くことになる。

**frontend を書き直さない理由**: アクセシビリティ対応（コントラスト AA 準拠、
タップターゲット、高コントラストテーマ、色以外の識別手段）、TTS、文字盤、定型文、
緊急ボタンが入っている。捨てると失われる実質的な作業がある。構造
（`features/*/{data,domain,providers,presentation}`）自体は妥当で、欠陥は
特定できる場所にある。

## 5. フェーズ

### 決定を守らせる仕組み（フェーズ設計の前提）

ADR を書くだけでは足りない。**実装担当が全 ADR を読んで回ることはない**ので、
「前提を確認せずに改修を依頼された」場合に新しい負債が作られる。
ADR は pull（読みに行く）であり、失敗は push（読まずに始まる）で起きる。

有効なのは3層で、上ほど強い。

| 層 | やり方 | なぜ効くか |
|---|---|---|
| **A. 消す** | 選択肢そのものを無くす（依存を消す、受け取る型を作らない） | **読まずに実装しようとすると物理的に詰まる。** 意志に依存しない |
| **B. 押し出す** | `CLAUDE.md` / `AGENTS.md` に決定の1行要約を置く | 自動で読み込まれる唯一のチャネル。`docs/adr/` は読みに行かないと届かない |
| **C. ゲートを張る** | 「負債を作る**行為**」を CI で検出し、ADR の引用を要求する | **決定は無限に増えるが、負債を作る行為は有限。** 事前に全決定を書かなくても「決定が要る場面」を検出できる |

C が本命である。今回で言えば、`ai_conversion_logs` テーブルを足した時点で
「このテーブルを読むのは誰か」という問いがその場で出ていたはずだった。
**「これは存在すべきか」を問う工程を、人の心がけから CI へ移す。**

この3層を各フェーズに埋め込む。守りの検査は、**それが守る対象と同じフェーズ**に置く
（初版は検査をすべて Phase 4 に置いており、最も大きな改修を行う Phase 2・3 が
無防備になっていた）。

#### ADR ごとの守り（この表が実効性の一覧である）

| ADR | 破る改修の例 | 守り | 層 | 入る Phase |
|---|---|---|---|---|
| 001 backend ステートレス | 「変換履歴をサーバーに残して」 | DB 系依存を削除。足すには依存追加が要り、ゲートが発火 | A + C | 1, 2 |
| 002 `memory://` | 「複数インスタンスで動くように」／`memory://` のまま worker / replica を増やす | `redis` 依存を削除 ＋ 起動ガード（同一コンテナ内のみ検出）＋ replica 上限は IaC 側の契約（デプロイ時に必須） | A + C | 1, 2 |
| 003 エラーは型 | `logger.error(f"{e}")` と書く | `str(exc)` を受け取る型が無い ＋ `grep` ゲート ＋ `mypy --strict` | A + C | 2 |
| 004 設定は不変 | `from config import settings` | Application Factory ＋ `pytest-randomly` ＋ `mypy --strict` | A + C | 2 |
| 005 1概念1真実 | 「タグ機能を追加」→ 2つ目の実装 | Hive スキーマ許可リスト（**永続を伴う場合のみ**） | C | 3 |

**正直な穴**: ADR-005 は、永続フィールドを伴わない重複（UI ロジックだけの二重実装）を
捕まえられない。`features/favorite/` と `features/favorites/` がまさにその形だった。
自動検査は原理的に不可能なので、Phase 4 の定期棚卸しで拾う。**ここだけは
「仕組みで防ぐ」に到達できていない**と明示しておく。

#### Tsumiki の扱い — 境界を引き直した

初版は Tsumiki を一括で遠ざけていたが、**ワークフローと個別スキルは別物**である。

> **単発の分析・壁打ち道具は採る。成果物を積み上げるワークフローは採らない。**

| 採る | 理由 |
|---|---|
| `adr-rubber-duck` | 出力先が `docs/adr/`、ヒアリング構造が `{背景と課題, 制約条件, 検討した選択肢, 決定, 決定理由, 影響}` で**本計画の完了条件と一致**。既存 ADR をスキャンして置き換え候補も出す |
| `dcs:impact-analysis` | **負債ゲートの pull 版。** ゲートは「書いた後に止める」が、これは書く前に触る範囲を出す。「そもそも必要か」を問う契機になる |
| `dcs:state-transition-analysis` | Phase 3 の `PersistenceState`（Ready / RecoverableFailure / Unavailable）とお気に入りの状態モデル設計に直結 |
| `ipa-security-check` | IPA 原典の**出典（文書名・章・ページ・URL）を必ず付ける**。8周の失敗は「反証不能な指摘が8割」だった。**出典付きの指摘は原典で決着する** |
| `dcs:edgecase-analysis` | 条件付き。**「洗い出した事例を1つずつ潰す」ではなく「洗い出しから不変条件を1本引く」ために使う**（事例の列挙は終わらない、が8周の教訓） |
| `rev-requirements` / `rev-specs` | Phase 5 で現行 `docs/spec/` と突き合わせ、乖離を出す。privacy-policy と実装の食い違いはこれで拾えた可能性がある |

| 採らない | 理由 |
|---|---|
| `dev-plan` → `dev-impl` → `dev-run` → `dev-verify` | `docs/dev/plans/<name>/reports/` に成果物を積む設計。**恒久成果物が工程記録になる**点が Phase 5 の判断基準に反する |
| `task-breakdown` | 同上 |

**注意**: `dcs:*` は `.dcs/` に出力する。`.gitignore` に追加済み
（未設定だと分析結果がコミット対象になり、「また工程記録が溜まる」形になる）。

#### OpenSpec を使う条件

Tsumiki との構造上の違いが1つあり、それが採否の根拠になる。

```
Tsumiki : docs/implements/ に299ファイルの工程記録が蓄積。仕様は成果物ではなかった
OpenSpec: openspec/specs/<capability>/spec.md が恒久。change の delta は archive 時に
          specs へ吸収される。ただし change 本体は削除されず changes/archive/ へ
          移動・保存される（openspec-archive スキルの実挙動。「消える」は
          自前で仕組み化しない限り起きない）
```

**恒久成果物が「仕様」であって「工程記録」ではない。** これは Phase 5 の判断基準
（「入力」か「実行可能」なものを残し、「工程の記録」は捨てる）と一致する。
OpenSpec をやめても `openspec/specs/` は素の Markdown として残る。

もう1つ、`openspec-propose` の **planning boundary**（「計画成果物のみを作る。
ユーザーが実装しろと言っていても同じ応答で実装を始めてはならない」）が、
**「改修依頼 → いきなり実装」をスキル規約として止める**（ツール本体の強制ゲートではなく、
効くのはスキルの指示に従う範囲。だから C 層のゲートを併用する）。
今回の問題への直接の対策になる。

ただし OpenSpec も CLI とスキルに依存した手法であり、同じ轍を踏みうる。条件は3つ。

1. **`openspec/specs/` だけを恒久成果物とする。** ツールの archive は `changes/archive/` への
   **移動・保存**であって削除ではないため、「捨てる」を実行可能にする:
   **`openspec/changes/` を `.gitignore` に入れ（設定済み）、CI で配下の tracked ファイルを
   禁止する（Phase 1 のゲートに含める）。** ここを曖昧にすると 299 ファイルが
   名前を変えて再生産される
2. **最初の大改修と同時に学ばない。** 実行順序が 1→3→2 になったため（ADR-007）、
   導入は **frontend フェーズ（Phase 3）の後半**——お気に入り・永続化状態を
   「仕様として書き取る」段階——からにする。フェーズ前半の状態モデル設計・修正は
   OpenSpec なしで行う。**最初の2 capability は既に実装された内容の baseline 書き取り**
   であり、propose → 承認 → apply のサイクル対象外。planning boundary と delta 管理が
   実際に効き始めるのは、その後の change から（再レビューの指摘を明文化——
   実装後の仕様書き取りに planning boundary は適用しようがない）
3. `openspec/config.yaml` の `context:` に技術スタックと ADR の要約を書く
   （これも B の押し出しチャネルになる）

検討した却下案: **OpenSpec を採らず、ADR・現行仕様・実行可能な検査の3点だけを残す**
（独立レビューの提案）。delta 管理と planning boundary の価値を取ってなお採用するが、
条件1が破られた（changes/ 配下に tracked ファイルが現れた）時点でこの却下案へ戻す。

#### OpenSpec の運用サイクル

| 局面 | スキル | 何が起きるか |
|---|---|---|
| 改修依頼を受けた直後 | `openspec-explore` | **書かない。** 問題を整理し「そもそも必要か」を問う。ADR / spec の作成すら、対象を名指しして yes/no を取ってから |
| 何を作るか固まった | `openspec-propose` | `proposal.md`（何を・なぜ）／`specs/` delta（システムが何をすべきか）／`design.md`（どう）／`tasks.md`（手順）を生成して**停止する** |
| 人が承認した後 | `openspec-apply` | `tasks.md` を順に実装。`openspec status` で進捗が追える。**SDD は使わない**（§5「subagent-driven-development を使う条件」条件5） |
| 実装完了 | `openspec-archive` | delta を `openspec/specs/` へ吸収し、change を archive |
| 途中で方針変更 | `openspec-update-change` | 計画成果物だけ改訂（コードは触らない） |

**propose と apply の間に人の承認が挟まる**（planning boundary）。
これが「改修依頼 → いきなり実装」を止める中核である（規約であって機械的強制ではない）。

**1つの change を大きくしないこと。** `tasks.md` が長大になると
「1周10〜15件をまとめて直す」が再演される。**change の粒度は完了条件7
（400行 / 12ファイル）に合わせる。**

#### subagent-driven-development を使う条件

Phase 2・3 の実行には `superpowers:subagent-driven-development`（タスクごとに新しい
implementer subagent を出し、タスクレビュー＋最終全体レビューを行うスキル）を使ってよい。
スキル本文を確認済み: **8周対策と同型の停止条件を内蔵している**——fix loop は5ラウンド上限
（breaker）で、上限では裁定して parked（却下の記録）、再レビューはスコープ固定
（触っていないコードの新指摘は台帳行き）、Minor はループに入れず台帳直行。
工程記録（ledger・レビューパッケージ）は git-ignored の workspace に置かれ完了時に
削除されるため、恒久成果物ルールとも整合する（採用初回に ignore が効いているか確認する）。

条件は5つ。

1. **入力はタスク分解済みの実装計画**。各フェーズ着手時に `superpowers:writing-plans` で
   work package を task 化する（本計画の「着手時に分解」と同じ工程）。
   タスク粒度は完了条件の 400行 / 12ファイルに合わせる
2. **task reviewer の constraints block に本プロジェクトの拘束を書き写す**:
   該当 ADR の要約・テスト規律（モックは SDK 境界のみ・完全一致アサーション禁止）・
   そのフェーズの完了条件。Critical / Important / Minor は P0 / P1 / P2 に写像する
3. **2系統レビューはタスク粒度でなくマージ境界で課す**。タスクごとのレビューは
   SDD の単系統でよく、マージ前の最終 whole-branch レビューを2系統
   （SDD の final reviewer ＋ Codex）にする——層3「PR ごと・2系統」との整合
4. **消える記録を昇格する**。フェーズ末に ledger の ruling・parked・deferred を
   台帳 #85 へ転記し、決定に触れる ruling は ADR へ昇格する（ledger は完了時に消える。
   「判断を状態を持たない場所に置かない」の原則）
5. **`openspec-apply` と役割を分け、併用しない**。OpenSpec の change として始まった改修は
   `openspec-apply` が実行する——1 change は完了条件の粒度（400行 / 12ファイル）に収まる
   実質1タスクで、subagent 分業のオーバーヘッドが利益を上回らない。change が複数タスクに
   割れるほど大きいなら、それは SDD を持ち込むシグナルではなく **change を分割する
   シグナル**である。SDD が担うのは OpenSpec 管理外のフェーズ計画
   （Phase 2 の書き直し・Phase 3 前半）のみ

**Phase 1 では使わない**——工程が密結合（ゲート → フック → CI → 発火確認）で、
`update-config` によるフック設定は権限確認を伴う対話作業のため。AST ゲート＋fixture のみ
独立タスクとして単発の subagent 切り出しが可能。なお負債ゲートの `PostToolUse` フックは
subagent の Edit / Write にも発火するので、Phase 1 のゲートが implementer を守る関係になる。

### レビューの層

**レビューは必須である。** 8周で問題だったのは「レビューの置き場所と入力」であって、
レビューそのものではない。5層に分ける。

| 層 | いつ | 何を見る | 8周との違い |
|---|---|---|---|
| **1. 前段（実装前）** | 着手前 | `dcs:impact-analysis` ＋ 該当 ADR の確認 | **「存在すべきか」をここで問う。** 差分レビューでは原理的にできない |

```
  config.py      RuntimeConfig(frozen=True)。secret は SecretStr、DSN は無い
  routes.py      POST /ai/convert, POST /ai/regenerate, GET /health
  ai/            プロバイダ client（lifespan で生成）+ プロンプト
  errors.py      ErrorCode(StrEnum) と SafeError。str(exc) を受け取る口を作らない
  logging.py     stdout への構造化ログ。ユーザー由来の内容を含めない
```

順序: 決定1（DB削除）→ 決定2（`memory://`）→ Application Factory → エラー型 → 設定の不変化。
実行は `superpowers:subagent-driven-development` を使ってよい（§5 の4条件を守り、
着手時に `superpowers:writing-plans` で task 分解する。逐次 dispatch でこの順序どおりに進める）。

#### A（消す）— 依存を削除して、選択肢そのものを無くす

`backend/requirements.txt` から5行を削除する。

```
sqlalchemy==2.0.44
alembic==1.18.3
asyncpg==0.31.0
psycopg2-binary==2.9.11
redis==8.0.1
```

**これが ADR-001 / 002 の実効的な守りである。** 以後「DB に保存して」という改修は
**依存追加という目立つ差分**を伴い、Phase 1 のゲートが発火する。ADR を読まなくても、
実装しようとした時点で一度止まる。

同じ発想を型にも適用する。`errors.py` は `ErrorCode` と `SafeError` しか受け取らないので、
`str(exc)` を渡せる引数がシステム内に存在しなくなる（ADR-003）。

#### この Phase で入れる検査（ADR-003 / 004 / 006 を実行可能にする）

守る対象と同じフェーズに置く。新 backend はレイヤが最初から綺麗なので、
契約を書くコストが最も低いのがここ。

- `import-linter` — レイヤ契約を CI で強制（ADR-006）
- `mypy --strict` — `SecretStr` / `ErrorCode` の取り違えを型で検出（ADR-003 / 004）
- `pytest-randomly` — グローバル状態への依存を露出させる（ADR-004）
- `grep` ゲート — `str(exc)` / `str(e)` / `format_exc` が `app/` に0件（ADR-003）
- 起動ガード — プロセス数>1（`WEB_CONCURRENCY` / uvicorn workers）かつレート制限ストレージが
  in-memory なら起動失敗（ADR-002）。**検出できるのは同一コンテナ内の worker まで**——
  single-worker × 複数 replica は素通しするので、replica 上限は ADR-002 のデプロイ側契約
  （IaC 固定 or 上流レート制限）で縛る
- stdlib `logging` の直接 import が `app/logging.py` 以外に0件、**`print(` / `sys.stderr` /
  `traceback.print_exc` も `app/` に0件**（stdout / stderr へ書けるのは `app/logging.py` のみ。
  ADR-003。grep は `logger.error(f"{exc}")` や `print(exc)` を捕まえられないため、
  受け口の型と canary 注入検査を主体にする）
- subprocess import smoke — 外部境界を封じた環境で `python -c "import app.main"` が
  外部アクセスゼロで完了する（ADR-004。代入を伴わない副作用呼び出しも捕まえる）

**テストは捨てて書き直す。** 現在 9,221行のうち assert は7%で、誤った仕様を固定し
（存在しない `unix` スキームを正解として要求）、漏えいシンクを36箇所でモックしている。
書き直す backend に対しては負の資産である。到達点は約1,500行、層は3つ——
プロバイダ SDK を `respx` でモックした API テスト、設定組み立ての単体テスト、
記号入りキーを含む起動 smoke。

境界（seam）をどこに置くかは `mattpocock-skills:codebase-design` の語彙を使う。
**モックは外部 SDK の境界にのみ置き、自分の関数には置かない。**

#### テストは2系統で書く（TDD だけでは足りない）

**要件からテストを起こす限り、要件に無いバグは永久に出ない。**
`%` を含むパスワードで DB に接続できないバグは、どの要件にも書かれていないため
418テスト緑のまま生き残った。だから2系統要る。

| | A. 仕様テスト | B. リスクテスト |
|---|---|---|
| 問い | **要件を満たしているか** | **壊れやすい所が壊れていないか** |
| 出所 | 受入基準、`openspec/specs/` の delta | **3つの源**（B-1 一般的な観点／B-2 プロダクト固有／B-3 過去の欠陥）。`docs/verification-principles.md` |
| 書き方 | **TDD**（赤 → 緑 → リファクタ） | TDD にならない（赤にする対象が仕様から出てこない）。過去の欠陥の形をリスト化し、新しいコードに当てる |
| 陥りやすい罠 | **実装のスナップショットを仕様として固定する**（`unix` スキームの件） | 事例の列挙に終始し、不変条件に至らない |

**過去の事例だけを出発点にしない。** それ自体が「事例の列挙」になり、8周と同じ形になる。
3つの源から引く（詳細は `docs/verification-principles.md`）。

新 backend で当てる B の観点:

| 源 | 観点 | テストの形 |
|---|---|---|
| B-3 | 設定の組み立て → 実接続 | 記号（`%` `@`）入りの値で起動 smoke |
| B-3 | 境界での例外変換 | 例外を注入し、**全シンク**（stdout / stderr / ログ / HTTP ボディ）を観測 |
| B-3 | 環境ガード | **両方の環境で**検証する（片方だけ通して破れた前例がある） |
| B-3 | 起動 | `python -c "import app.main"` の出力全体を grep |
| **B-1** | 境界値 | 空文字列・上限長・絵文字・結合文字を各入力へ |
| **B-1** | 失敗注入 | AI プロバイダ SDK が落ちる／遅い／不正な応答を返す |
| **B-1** | べき等性 | 同一リクエストの二重送信、リトライ |
| **B-1** | 時間 | `AI_CALL_DEADLINE_SECONDS` の締切超過 |
| **B-1** | 設定の組み合わせ | 環境 × APIキー有無 × プロバイダの掛け算 |
| **B-2** | 応答時間 | AI 変換 平均3秒以内（要件）を実測 |
| **B-2** | オフライン遷移 | 変換中に接続が切れたときの応答 |

**A と B の比率を測る手段が mutation kill rate である。** 本数では測らない。

#### 新しいテストが同じ罠に落ちないための検査（プロジェクト固有スキルを作る）

今回の最も鋭い発見——`test_socket_uri_keeps_its_path` が存在しない `unix` スキームを
**正解として固定**し、それが手書きの `| {"unix"}` を生んだ——に対する既存の道具は
どこにも無い。

判定基準は言語化できている。

> **このアサーションは、実装を安全側に変えたときに落ちるか。**
> 落ちるなら、それは仕様ではなく現在の実装のスナップショットである。

完全な自動化は難しいが、次は機械的に拾える。`skill-creator` で
プロジェクト固有スキルとして手順化する。

```
- 外部ライブラリの定数・集合を、テスト側でハードコードして期待している箇所
- 診断メッセージ・ログ文字列の完全一致アサーション
- 例外クラス名やライブラリ由来の文字列を期待している箇所
```

補助として `mutmut` を config・エラー処理に限定して回し、**mutation kill rate** で
テストの実効性を測る（本数では測らない）。

#### この Phase の締めに `tsumiki:ipa-security-check` を回す

IPA 原典（「安全なウェブサイトの作り方 改訂第7版」ほか）に基づく静的検査で、
**検出項目に出典（文書名・章・ページ・URL）を必ず付ける**。

これが効く理由は、8周の失敗が「反証不能な指摘が8割」だったことにある。
**出典が付いた指摘は反証可能で、「これは本当に問題か」の議論が原典で決着する。**
AI レビューの水掛け論とは性質が違う。`ipa-security-guide` で検出結果を
優先順位付きの対応リストに変換できる。

### Phase 3 — frontend の正しさを直す（5〜8日）

利用者に直接届く順に並べてある。

**道具**: 1 と 2 は状態モデルの設計なので、着手前に
`tsumiki:dcs:state-transition-analysis` で対象データ（永続化状態・お気に入り）の
遷移フローと依存関係を洗い出す。境界の位置は `mattpocock-skills:codebase-design`。

着手時に `superpowers:writing-plans` で work package を task 分解する）。

**テストは Phase 2 と同じ2系統で書く。** frontend の B は、
利用者が発話で訂正できず端末内にしかデータが無いため、**B-2（プロダクト固有）が最も重い**。

| 源 | 観点 | テストの形 |
|---|---|---|
| B-3 | 変換層（mapper） | **往復テスト**（domain → storage → domain が恒等） |
| B-3 | 永続化の失敗 | 失敗を注入し、**利用者への通知**を検証 |
| B-3 | 状態の二重表現 | 真実が1つであることの構造検査（Hive 許可リスト） |
| B-3 | レイアウトの重なり | 常設ボタンが文字盤のキーを覆わないか（実際に起きた） |
| **B-2** | **操作の取り消し** | 削除・送信・読み上げに undo があるか。無いなら確認を挟むか |
| **B-2** | **誤タップ・連打** | 同一ボタン連打、隣接キーの同時タップ |
| **B-2** | **緊急ボタン** | 常に遮蔽なくタップできるか／誤発報に確認があるか |
| **B-2** | **データ喪失** | 保存失敗を利用者に伝えるか。再起動で消えないか |
| **B-2** | TTS の割り込み | 連続読み上げ、停止、読み上げ中の画面遷移 |
| **B-2** | オフライン遷移 | オンライン → オフラインの遷移中に AI 変換を開始 |
| **B-2** | アクセシビリティの組み合わせ | 大フォント × 高コントラスト × 横向きでレイアウトが破れないか |
| **B-1** | ライフサイクル | 空の状態 → 操作 → 再起動 → 状態が残るか |
| **B-1** | リソース枯渇 | 保存領域が一杯・権限が無いときの挙動 |

**B-2 の導き方**は「**この製品の利用者にとって、何が起きたら最悪か**」を問うこと。
機能や利用者像が変わったら見直す。この観点群は**当事者検証を経ていない仮説**である——
「確認ステップを挟む」対策は「できるだけ少ない操作で伝える」という製品目的と衝突しうるので、
導入時は要件と突き合わせて選ぶ。formative usability test の要否・時期は ADR-007 で決める。

1. **永続化の状態を明示する。** いま Hive が開けないと `repository_providers.dart` が
   黙って `null` を返し、インメモリで動き続ける（`hive_init.dart` が意図した設計として明記）。
   **発話支援アプリで「保存できたように見えて消える」は、起動しないことより重い。**
   `sealed class PersistenceState { Ready / RecoverableFailure / Unavailable }` にして、
   保存されないことを利用者に伝える。
2. **「お気に入り」を1つの真実にする。** いま `HistoryItem.isFavorite`（書かれるが常に
   `false`、UI は読まない）、`features/favorite/`（ロジック）、`features/favorites/`（UI）、
   さらに `PresetPhrase.isFavorite`（Hive field 3 で永続・UI が読む・favoriteNotifier と
   双方向同期——独立レビューが検出）の**4箇所**に散っている。正は `favoriteProvider` なので、
   `HistoryItem.isFavorite` と `PresetPhrase.isFavorite` を Hive migration で削除し、
   参照を寄せる。キーは内容テキストではなく id にする（詳細は ADR-005）。
3. **往復テストを feature ごとに1本。** UI → provider → repository → storage → 戻り。
   層を飛ばして下だけを叩くテストは、単体では合格にしない。
   （`isFavorite` のバグは Hive アダプタのテストが緑のまま生き残った。バグは
   その上の変換層にあった。）
4. **E2E は「書き直す」前に「切り分ける」**（Issue #84）。下記。

#### E2E の方針

**現状**: 7本中 `app_startup_test.dart` のみ CI で緑。5本が Issue #84 で一時除外、
2本（`ai_conversion_e2e_test.dart` / `performance_profiling_e2e_test.dart`）が恒久除外。

**まず切り分ける——実施済み（2026-08-29、Phase 0 で前倒し）: 実ブラウザで埋まった。**
分岐2（環境／テストの問題）が確定。以降のこの節は「テストを書き直す」前提で読むこと。

Issue #84 は「テストの陳腐化と考えられます」と書く一方、同じ issue にこうある。

> `ClearAllButton(enabled: inputBuffer.isNotEmpty)` の分岐で「5文字タップ後もバッファが空」と
> 確認できるため、単なる1フレーム遅れではありません。

**タップしても入力バッファが埋まっていない。** headless web 固有なら環境問題だが、
**実ブラウザでも起きるなら P0 のアプリ不具合**である。文字盤入力はこのアプリの基本機能で、
これが動かなければアプリの意味がない。

```
1. flutter run -d chrome で実際に5文字タップし、バッファを見る
2. 埋まる     → 環境／テストの問題。テストを書き直す
3. 埋まらない → P0 のアプリ不具合。E2E より先に直す
```

**この切り分けを飛ばして書き直すと、アプリの不具合に合わせてテストを歪める**ことになる。
`docs/verification-principles.md` の「自分が書いた文書を事実として扱わない」の実例であり、
メモリにも「陳腐化であり退行ではない」と記録されていたが、**未検証の推測だった**。

**次に範囲を決める。** いま7本あるが選定基準がない。E2E は高価で不安定なので、
**「壊れたらアプリとして使えない」経路だけ**に絞る。

| 残す | 理由 |
|---|---|
| 起動 | 既に緑。最も安い保険 |
| 文字盤で入力 → TTS で読み上げ | **中核。これが動かなければアプリの意味がない** |
| 定型文の登録 → 呼び出し | **永続化を通る**（Phase 3-1 の対象） |
| 緊急ボタン | **安全に関わる** |

| E2E から外す | 代わりに |
|---|---|
| テーマ切替・アクセシビリティ | **Widget テストで足りる**（`test/accessibility/` に9本ある） |
| `ai_conversion_e2e_test.dart` | Phase 2 で backend を書き直した後、**モックプロバイダ相手の E2E として復活**できる |
| `performance_profiling_e2e_test.dart` | **nightly の定期ジョブへ移す。** CI をブロックさせない |

**ADR-005（1概念1真実）は原理的に完全には検査できない。** 永続フィールドが増える形
（`isFavorite` がまさにこれ）は上の許可リストで捕まるが、UI ロジックだけで重複する場合は
捕まらない。残余への対処は Phase 4。

導入は**このフェーズの後半**から（§5「OpenSpec を使う条件」条件2。実行順序が

### Phase 4 — 検査しきれない残余に対処する（1〜2日）— **完了（2026-09-06）**

Phase 1〜3 で入れた検査は「決定の違反」と「負債を作る行為」を捕まえる。
**捕まらないものが2種類残る。**

**1. 同じ概念の2つ目の実装**（ADR-005 の残余）

永続フィールドを伴わない重複——UI ロジックだけで同じことをする実装——は
自動検査できない。`features/favorite/` と `features/favorites/` がまさにこれだった。

対処は**定期的な棚卸し**しかない。月1で次を測る。
**この項目リストが、そのままプロジェクト固有スキルの中身になる。**

```
コードの重複・死蔵
- 同じ概念を扱うディレクトリ／provider が複数ないか
- 定義のみで参照ゼロの型・関数はないか

仕様と実装の乖離
- 実装から遅れているテスト・ドキュメントはないか
- 仕様（privacy-policy / ADR）と実装が食い違っていないか
- 置き換えられるべき ADR が現役のまま残っていないか

★ 守りの仕組み自体の陳腐化
- AGENTS.md の道具リストに挙げたスキルが、すべて実在するか
- 各道具が、その目的にとってまだ最適か（より良いものが出ていないか）
- 完了条件に書いた grep / 検査が、いまも意味のある対象を指しているか
- 負債ゲートの7項目が、実際に発火する状態にあるか。項目自体に漏れが出ていないか
- 文書が参照するファイル・パスが実在するか（経緯記事が参照3箇所を残したまま削除された前例がある）
- `openspec/changes/` に archive されず滞留した change が無いか
```

**★ を入れる理由**: 守りの仕組みも文書であり、**同じ理由で陳腐化する**。
`docs/verification-principles.md` の「自分が書いた文書を事実として扱わない」は、
この計画自身と AGENTS.md にも当てはまる。

道具リストは特に腐りやすい。スキルは外部プラグインなので、**こちらが何もしなくても
消えたり改名されたりする**。「目的は固定、道具は差し替え可能」と書いた以上、
**道具が生きているかを定期的に確かめる工程がなければ、その原則は絵に描いた餅**になる。

負債ゲートについても同じで、「ゲートが存在すること」と「ゲートが機能すること」は別である
（Phase 1 の完了条件で一度は確認するが、その後 CI やフックの設定が変わりうる）。

**この棚卸しは差分レビューではできない。** 全体を見る別の工程として回すこと
（8周のレビューが `core → db → core` を一度も見つけなかったのと同じ理由）。

**既存のスキルに該当するものが無い**（`refactor-cleaner` はデッドコード除去であって
概念の重複検出ではない）。**これは明確にスキルの形をしている**——繰り返し実行する
判断手順なので、`skill-creator` でプロジェクト固有スキルとして作る。
手順を文書に書くだけだと、月1で誰も実行しない。

Phase 4 を待たずに作ってよい。作った時点から回せる。

**2. テストの検証力そのもの**

テストの本数は品質を示さない（旧 backend は本体の2.6倍あって assert は7%だった）。
`mutmut` を config・エラー処理・mapper に限定して回し、**mutation kill rate** を指標にする。
本数ではなく、実際に欠陥を殺せるかを測る。

### Phase 5 — docs を整理する（2〜3日）

**判断基準**: 「入力」か「実行可能」なものは残し、「工程の記録」は捨てる。

| | 対象 | 扱い |
|---|---|---|
| 残す | 要件（EARS）・受入基準 | Tsumiki の出力としてではなく**プロダクト仕様として引き取る** |
| 残す | アクセシビリティ基準（WCAG AA、44/60px、フォント3段階、テーマ3種） | このプロダクトの核。**テストとして実行可能にする** |
| 残す | privacy-policy.md | 実装に合わせて書き直す（決定1で自動的に整合する） |
| 捨てる | 【】記法コメント | frontend lib 約1,200行ほか |
| 捨てる | 🔵🟡🔴 信頼性レベル記号 | 生成時点の確信度であって、コードの性質ではない |
| 捨てる | tech-stack.md の実在しない構成記述 | `infra/` `services/` `core/database.py` `tests/test_services/` |

**正本を1つずつ決める**: API は OpenAPI、環境変数は `RuntimeConfig`、UI 仕様は Widget テスト、
データ保持は ADR + privacy-policy。

**道具**: `tsumiki:rev-requirements` / `rev-specs` で実装から要件・仕様を逆生成し、
現行の `docs/spec/` と突き合わせて乖離を出す。privacy-policy と実装の食い違い
（「保存されません」と書いて保存していた）は、この方法なら拾えた可能性がある。
**逆生成した文書をそのまま正本にしないこと**——差分を出すための道具であって、
出力を積むと工程記録が増えるだけになる。
