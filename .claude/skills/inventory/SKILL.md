# 棚卸し

**数えるのは機械、判断は人。ここでは直さない。** 見つけた問題は `docs/ledger.md` に 1 行で書き、直すのは別の作業。

## 手順

1. `scripts/inventory.sh` を実行し、出力を手元に置く（数字はすべてここから取る。推測で書かない）。
2. 下の観点を順に当てる。各観点で「該当なし」も明示する
3. `docs/ledger.md` に追記する。新しい問題は `- [ ] L-NN 1 行 — 出所`。解消していた `[ ]` は `[x]` に。**`[x]` と `[-]` は行ごと消す**（履歴は git。前回の棚卸し以降に付いた印も含む）。「計測」節の表を最新 1 回分に書き換える
4. PR を作り、本文に `Closes #<棚卸し Issue>` と、観点ごとの結論を 1 行ずつ書く（作業の記録は PR。Issue には書かない）

## 観点

### 1. コードの重複・死蔵
- 同じ概念を扱う provider・ディレクトリが 2 つ以上ないか（`grep -rn 'Provider<' lib | sort` で名前を並べて目視）
- 定義のみで参照ゼロの型・関数はないか（backend は `ruff` の未使用、frontend は名前で `grep -rn` して定義以外の出現が 0 のもの）

### 2. 仕様と実装の乖離
- privacy-policy.md・ADR の記述と実装が食い違っていないか（保存先、送信先、権限。manifest と `Info.plist` を現物で見る）
- `docs/spec/kotonoha-requirements.md` の各要件に対応するテストがあるか。無い要件は 1 行で挙げる
- 置き換えられた決定が未卒業のまま残っていないか（索引の「検査」列が埋まった ADR は卒業させる）

### 3. 守りの仕組みの陳腐化（★ 最重要）
- AGENTS.md の道具表: `inventory.sh` の「道具の実在」で 有効=False か 定義=なし の行は、**現物（plugin cache と settings）を確かめてから**表から降ろす（消さない。降ろすだけ。機械の出力だけで降ろさない）
- 索引（AGENTS.md と `docs/adr/README.md`）の「関わる行為」列と `scripts/adr-touch.sh` の case が、実在するパスを指しているか。README の「赤の見方」は年 1 回、実際に壊して赤を見る
- 完了条件の grep（`backend/scripts/gates.sh`）が、いまも意味のある対象を指しているか
- 「負債を作る行為」8 項目の受け皿（層 1・3・5）が動いているか。規律 4 の yes/no 表が本文に無い PR は直近 1 か月で何本か。`scripts/adr-touch.sh` を手元で流して判断が変わった実例はあるか（半年ゼロなら消す）
- `inventory.sh` の「実在しないパス参照」「出力ゼロの仕組み」「破棄条件なし」の各行
- `openspec/` に tracked ファイルが無いか（CI で見ているが再確認）

### 4. テストの検証力
- 実装のスナップショットになっているテストの兆候: 外部ライブラリの定数を期待値にハードコード／診断文言の完全一致／例外クラス名の期待（`grep -rn "assert.*==.*'" backend/tests`、`expect(.*, '` の文言を目視）
- backend の mutation kill rate（`cd backend && PATH=.venv/bin:$PATH make mutation`。対象は config / errors / auth / ratelimit）。前回より下がっていたら原因を 1 行

### 5. 計測
- 核の行数（上限 120）、未卒業 ADR の本数（上限 5）と各行数（上限 60）
- 台帳の 未対応 / 対応済み / 却下（入口・出口比）
- 出力ゼロの仕組み（90 日）

### 6. 目的との整合（仕組み自体が妥当かを問う。数えるのは機械、答えるのは人）
- `inventory.sh` の「直近 30 日のコミット（製品 / 全体）」は粗い数字（パスで数えるのでコメント整理も製品側に入る）。差分を見て「利用者の挙動か保存方式を変えた」ものを人が数え直し、ゼロの月は次の文書・検査の PR の前に理由を 1 行
- リリース条件 4 の人の作業（L-51・L-52・L-84〜L-86）が前回から動いたか。動いていなければ 1 行
- 各仕組み（`scripts/adr-touch.sh`、独立監査、ADR、台帳、この棚卸し）について「今月、判断が変わった実例」を 1 行ずつ。実例ゼロが 2 回続いた仕組みは廃棄候補として台帳へ
- **今の仕組みで解決できなかったことがないか**: 今月見つかった問題（台帳の新規行・事故・レビュー指摘）のうち、常設の仕組みの外で見つかったもの・防げなかったものを列挙し、構造を変えれば防げたかを 1 行ずつ問う。検査を足す案は選択肢に入れない（規律 8）
- 規律 9 の問い「この 1 か月の仕組み側の変更が完全に成功したら、利用者に何が変わるか」を PR 本文に 1 行で書く
- 四半期に 1 回（1・4・7・10 月）、下の付録の独立監査を行う。結果は台帳へ

## 付録: 独立監査の手順（規律 9。引き金: 保存・送信の経路を変える PR／ストア提出の前／四半期に 1 回）

**渡すもの**: リポジトリのパス、正本の一覧（`docs/privacy-policy.md`、`docs/spec/kotonoha-requirements.md`、`docs/adr/`、`AGENTS.md`）、PR が引き金なら対象の差分。**結論や見立ては渡さない。**
